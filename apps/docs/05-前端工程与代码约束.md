# 05 · 前端工程与代码约束

> 本章约束「前端代码怎么组织、怎么写、怎么测、怎么发布」。与根目录 `DEVELOPMENT_CONSTRAINTS.md` 对齐(技术栈/风格/命名/测试/性能),**不重复、不冲突**,只补充前端特有的落地细则。

## 1. 目录结构(MUST,Monorepo pnpm workspace)

> 规划结构(对齐 PDD §2.4「三端合一单 App,方案 F3」);当前仓库 `apps/pc`、`apps/mobile` 为既有骨架,演进时向此结构收敛。

```
apps/
  web/                 # 三端合一单应用(消费/经营/监管按角色路由),唯一部署产物
  pc/                  # (既有)PC 骨架 → 演进为 apps/web 或保留为 Electron 壳入口
  mobile/              # uni-app 移动端(H5/小程序)
  docs/                # 本目录(前端设计规范)
packages/
  ui/                  # 公共组件库(AntD 封装)
  assistant/           # 助手侧边栏组件(J 模块,三端复用)
  api-client/          # API 客户端 + TS 类型(OpenAPI 按模块生成)
  shared/              # 常量/工具/鉴权/RBAC 路由守卫
```

- 业务 feature 在 `apps/web` 内按模块组织:档案查询(A1/A2/A3)· 投诉工单(D2/G1)· 溯源扫码(T3)· 账户钱包(I1)· 用工发薪(C2/I2/I3)· 选品交易(T1/T4,M2)· 监管看板(DASH/A4)· 助手(挂载侧边栏)。
- 各 feature 独立开发、最后合并构建;跨 feature 复用一律下沉到 `packages/*`(MUST)。

## 2. 技术栈与版本锁定(MUST)

- PC:React 18 + TypeScript 5.6 + Vite 5 + Ant Design 5;Electron 33(套壳)。
- 移动:uni-app Vue 3;`@dcloudio/*` 必须锁定同一 build(当前 `3.0.0-4020920240930001`),禁止混版本。
- 包管理统一 pnpm 9.14(`packageManager` 锁定),`pnpm-lock.yaml` 入库;禁止混用 npm/yarn。
- 大版本升级走评审(对齐 G2/G3 门禁),不随业务提交夹带升级。

## 3. TypeScript(MUST,禁止降级)

- 保持 `strict` + `noUnusedLocals` + `noUnusedParameters` + `noFallthroughCasesInSwitch`。
- 禁止 `any` 泛滥:对外 API 类型以 `packages/api-client` 生成的类型为准;确需 `any` 须注释说明理由。
- 组件 props 显式类型;事件、回调、表单值结构化定义,禁止「一坨 string」传参。
- 枚举/状态常量集中在 `packages/shared`,与后端状态机对齐,禁止页面内重复定义魔法字符串。

## 4. 命名规范(MUST)

- 标识符一律英文:变量/函数 `camelCase`,组件/类 `PascalCase`,常量 `UPPER_SNAKE_CASE`。
- 组件文件名与组件名一致(PascalCase);页面/模块目录用语义英文,禁止拼音。
- CSS 类名/令牌:kebab-case,语义化(见 `02` §0)。
- 注释与文档用中文,标识符用英文(全局约束)。

## 5. 代码风格 / Lint / Format

- 遵循根 `.editorconfig`:UTF-8、LF、末尾换行、去行尾空格、2 空格缩进。
- **SHOULD(技术债)**:逐步引入 ESLint + Prettier 统一;当前缺失,提交前人工自查上述约束。
- 组件拆分:单一职责,单文件不宜过长(建议 <300 行);重复逻辑抽 hooks/utils。

## 6. 状态管理与数据流(SHOULD)

- 页面级状态:优先组件状态 + hooks;跨组件共享用轻量状态库(按团队选型,避免过早引入重方案)。
- 服务端数据:统一经 `packages/api-client` 请求,配请求态封装(loading/error/data),不在页面散写 fetch。
- 全局会话:鉴权令牌、用户角色/权限由 `packages/shared` 的鉴权模块管理,禁止页面各自读 localStorage 拼接(见 `06`)。

## 7. API 客户端约定(MUST)

- 所有后端调用走 `packages/api-client`,类型由后端 OpenAPI 按模块生成,**禁止手写接口类型导致漂移**。
- 统一处理:鉴权头、错误码映射(对接后端 §6.2 统一响应与错误码)、超时、重试、加载态。
- 敏感接口(支付回调、大模型对话)**只走服务端,前端不直连**(MUST,见 `06` §4)。

## 8. 性能约束(SHOULD,逐步达标)

- 路由/组件按需懒加载(`React.lazy` + 代码分割);控制首屏与包体积。
- 大列表虚拟滚动;表格分页 + 服务端筛选排序,不全量前端算。
- 避免无谓 re-render:合理 `memo`/`useMemo`/`useCallback`,列表项 key 稳定。
- 图片懒加载/压缩;监管看板大屏数据用聚合接口 + 按需刷新,不轮询全量。

## 9. 配置与环境(MUST,安全)

- 环境差异(接口域名、网关、第三方 key)走环境变量;提交 `.env.example` 模板,**不提交真实 `.env*`、不硬编码密钥**。
- 前端代码中出现的第三方 key 仅限「可公开、无敏感」类(如地图 key 需按平台策略限制),其余一律服务端下发。

## 10. 测试约束(MUST,逐步引入)

- 新代码单测覆盖率 ≥80%(行/函数/分支,对齐 SDLC SLO);关键业务逻辑(鉴权守卫、资金/信用展示、表单校验、脱敏函数)必须有测试。
- PC 端用 Vitest、移动端用 uni-automator(全局约束 SHOULD);前端测试框架当前缺失,随开发引入。
- 组件关键交互(资金二次确认、四态覆盖、权限路由)建议补组件/集成测试。

## 11. 构建与发布

- 构建:PC `tsc --noEmit && vite build`(类型检查门禁);移动 `uni build`(H5/小程序分别产出)。
- 发布:过本地门禁(`.githooks`)与 `commit-check`;不通过不得提交、`--no-verify` 不得绕过。
- 产物:PC Web 单包复用为 Electron 壳内容;H5/小程序产物分别部署/上传,版本号与提交对应可追溯。
