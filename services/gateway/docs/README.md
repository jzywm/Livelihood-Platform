# 网关服务（GATEWAY · Gateway）

> 微服务说明文档 · 依据《产品需求文档》（PRD v2.0）与《产品设计文档》（PDD v1.14）编写
> 本文档用于明确该微服务的**功能与质量基线**，支持后续扩展开发。功能口径以 PDD §5.16 / §3.1 为准，网关职责详设以《高并发架构演进设计》v0.5 §7 为准。

## 1. 服务概述

- **服务标识**：`gateway`（网关服务）
- **服务定位**：平台**唯一统一入口（API 网关微服务）**，承载接入层全部横切职责——路由转发、统一鉴权（JWT 验签 + Redis 吊销校验）、网关级限流、灰度分流、超时/熔断/降级、traceId 注入/透传、统一 Envelope 封装、HTTPS 终结。
- **对应模块**：平台级横切（无业务功能点；承载 PDD §3.1「API 网关与统一入口」拍板能力）。
- **里程碑**：**M1 后期独立部署**（M1 初期由应用内嵌统一 Filter + Nginx 过渡；独立部署后内嵌 Filter 降级为故障兜底路径）。
- **实现载体 / 技术栈**：Java 17 + Spring Boot 3.5 + Spring Cloud Gateway（WebFlux）+ Nacos（服务发现/配置热更新）+ Sentinel（网关适配）。
- **三端分布**：消费端 / 经营端 / 监管端 / 运营端**全部流量统一入口**（各端不直连领域服务）。
- **依赖服务 / 外部依赖**：Nacos（路由/服务发现/灰度配置热更新）、Redis（JWT 黑名单 + 限流计数，Redis+Lua 令牌桶）、KMS（JWT 签名密钥注入，密钥不出网关）、云 WAF/高防（DDoS/SQLi/XSS 前置）、Prometheus + Alertmanager（网关指标与告警）。
- **核心链路**：TLS 终止 → 云 WAF/高防 → JWT 验签 + 吊销检查（Redis）→ 网关级限流 → 路由转发 → 服务内越权校验（2002）与业务处理。

## 2. 背景条件

- **需求背景（解决什么问题）**：多端直连、多服务入口散乱、鉴权/限流口径不一、AI 链路成本失控与调用不可控——网关作为唯一入口统一收敛认证、鉴权、限流、签名、防重放与灰度分流（PRD §3.4、《非功能需求-信息安全与可靠性专项》§3.4；功能列表 J-12/K-02）。
- **前置条件（本服务运行前提）**：
  - M1 初期（独立部署前）：单体期应用内嵌统一 Filter（鉴权/JWT/限流/OpenAPI 收敛）+ Nginx（HTTPS 终结/静态资源/灰度分流）过渡；
  - M1 后期：GATEWAY 独立部署，前置条件齐备——无状态化（会话外置 Redis）、JWT 可吊销、traceId 规范（PDD §8.3 / 高并发 §8.2.2）；
  - 服务端间接口（各服务 x-external-interfaces）不暴露于网关（仅内网 + 内部 Token）。
- **平台红线约束（本服务需强落地）**：
  - 密钥不出网关——JWT 签名密钥 KMS 注入，网关内验签，不下发服务（R-03 数据分级口径）；
  - 管理端二次鉴权与业务越权校验（2002）在服务内完成，网关不越俎代庖；
  - 资金链路保护优先级最高（网关级限流/熔断先保资金接口）；
  - 前端不直连 Python 服务（AI 入口经网关/主站鉴权后转发，PDD §6.2 口径）。
- **里程碑边界**：M1 初期 = 内嵌 Filter + Nginx 过渡；M1 后期 = GATEWAY 独立部署（双实例）；M2 = 多实例全量 + Nacos 热更新 + K8s 金丝雀。

## 3. 主要功能（网关承载职责全集）

> 本节把散落在 PDD §3.1 / §6.2、高并发 v0.5 §7 的网关职责收敛为 GATEWAY 的完整承载清单；**不承载**项见 §5 边界。

### 3.1 统一路由与双语言转发

- 统一入口 `api.example.com/api/v1/{svc}/…`；M1 初期：Nginx → 单体应用内 Filter 路由；M1 后期起：Nginx → GATEWAY → 各域实例（Nacos 服务发现 + 灰度配置热更新）。
- 双语言路由：`/assist/*`、`/aicore/*` → Python 服务；其余 → Java 域。

### 3.2 统一鉴权链

① TLS 终止（网关/Nginx）→ ② 云 WAF/高防 → ③ 网关 JWT 验签 + 吊销检查（Redis）+ 限流 → ④ 服务内越权校验（2002）；管理端二次鉴权在服务内；密钥不出网关（KMS 注入）。

### 3.3 网关级限流

- IP / 账号 / 接口三级令牌桶（Redis+Lua）；两级体系：网关级（本服务）→ 服务级（Sentinel 热点参数/系统自适应，M2 全量）。
- AI 链路按账号强限（10 次/分/账号★）；资金链路保护优先级最高；网关超时/熔断 → 统一 503 + 友好提示；L3 服务允许短暂降级。

### 3.4 灰度分流

- M1 初期：Nginx 按 header/cookie/IP/百分比分流（功能开关 + 灰度标签）。
- M1 后期：GATEWAY 路由权重分流；M2：K8s 金丝雀（5%~10% 起步，指标劣化自动切回）。

### 3.5 超时 / 熔断 / 降级

- 统一超时分级：内部服务 1s / 第三方支付 3s / AI 5s（初值，评审 + 压测标定）；网关聚合超时按路由配置。
- 熔断护栏：Sentinel 网关适配；降级 = 统一 503 + 友好提示，不破坏业务状态。

### 3.6 traceId 与统一响应

- HTTP `X-Request-Id` 注入、MQ header 透传（SkyWalking/OTel，与主站一致）；统一 Envelope + 错误码（`services/_common/openapi.yaml` 口径）。

### 3.7 高可用与运维

- 网关双实例起步 + Nacos 健康检查自动摘除故障实例；网关**无状态**（配置 Nacos 热更新）。
- 兜底：GATEWAY 故障 → Nginx 直连单体降级路径（L3 可短暂降级）。
- 指标：每路由 QPS / P95 / 错误率 / 限流次数 → Prometheus；告警分级沿用 P0~P2 渠道。

## 4. 非功能性需求要求

### 4.1 全平台通用基线（所有服务共同遵守）

- **规模**：覆盖 ≈840 万；注册 ≥600 万、MAU ≥200 万、商户/机构 ≥10 万、DAU 峰值 ≈120 万。
- **性能**：核心读首屏 P95 ≤2s；核心写 P95 ≤3s；API P95 ≤500ms / P99 ≤1s（网关/应用预算 150ms，PDD §8.1.2）。
- **可用性分级 SLO**：L1 ≥99.95% / L2 ≥99.9% / L3 ≥99.5%。
- **容灾**：同城双活 + 异地灾备，RPO ≤15min、RTO ≤30min（L1）。
- **安全**：等保三级 + OWASP ASVS L2；TLS 1.2+；密钥 KMS/HSM。
- **数据**：审计日志 ≥6 个月；存证只增不改。

### 4.2 本服务专项要求

- **可用性等级：L1（≥99.95%）**——全平台流量唯一入口，是 L1 停机预算与容灾覆盖对象。
- **性能**：多一跳开销 ms 级（路由/验签/限流全内存 + Redis Lua 原子）；网关双实例 + 无状态水平扩展。
- **数据安全**：**无业务数据库**——不落业务数据；Redis 仅存 JWT 黑名单（短 TTL）与限流计数；JWT 密钥 KMS 注入、网关内验签；审计日志脱敏。
- **可观测**：每路由 QPS / P95 / 错误率 / 限流次数指标 + 告警分级（P0~P2）；traceId 注入/透传。

## 5. 职责边界（承载 vs 不承载）

| 承载（GATEWAY） | 不承载（服务内） |
|---|---|
| 路由转发、统一鉴权（JWT 验签 + Redis 可吊销校验）、网关级限流（IP/账号/接口）、灰度分流、HTTPS 终结、traceId 注入/透传、统一 Envelope 封装、超时/熔断/降级 | 业务权限细粒度校验（水平/垂直越权 2002）、资金幂等（Idempotency-Key）、业务状态机、协议聚合（不做 BFF 聚合层） |

- **与 AI 网关底座（K-02）的边界**：AI 网关底座是 AICORE 内面向大模型的**应用级网关**（模型路由/任务队列/置信度分级/全链路审计，Python 侧），**不并入 GATEWAY**；GATEWAY 是面向全部流量的**接入层网关**（Java 侧）。两者分层不同：`/aicore/*`、`/assist/*` 经 GATEWAY 鉴权/限流后转发至 Python 服务。
- **接口与数据库口径**：GATEWAY 无前端业务接口与业务数据库，故不设 `openapi.yaml`（业务接口 14 份以 `services/*/docs/openapi.yaml` 为唯一可手改源）与 `er.md`（无业务库，不适用 db-design 七章模板）；运维接口（健康检查/路由状态查询）待 M1 后期独立部署时补充。
