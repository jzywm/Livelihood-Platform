# 配送服务（DELIVERY · Delivery）

> 微服务说明文档 · 依据《产品需求文档》（PRD v2.3）与《产品设计文档》（PDD v1.0（基线））编写
> 本文档用于明确该微服务的**功能与质量基线**，支持后续扩展开发。功能口径以 PDD §5.15 为准，需求口径以 PRD §5.14（L 组，L-01~L-08）为准，车型兼容与骑手端以新增功能点 L-07/L-08（2026-09-11 设计先行，走规格书 §10 变更登记）为准。

## 1. 服务概述

- **服务标识**：`delivery`（配送服务）
- **服务定位**：本地配送（同城即时配送）下单/地址定位、订单状态机与全程跟踪、商家接单备货、运营调度看板、运力管理与位置轨迹存证，**以及骑手端任务/导航/位置共享与车型（电动车 + 汽车）兼容**。
- **对应模块**：L 组（L-01~L-08；L-07/L-08 为 2026-09-11 新增，走规格书 §10 变更登记）。
- **里程碑**：M2 交付；**骑手端 M2 交付、设计先行**（2026-09-11 由「骑手端后置」调整——骑手端页面 D-01~D-03 与骑手接口已设计，落地随 M2）。
- **实现载体 / 技术栈**：Java 17 + Spring Boot 3.5（模块化单体）；骑手端页面随 `apps/mobile`（uni-app，H5 + 微信小程序）落地。
- **三端分布**：消费端（配送下单 / 订单跟踪 / 查看骑手实时位置）· 经营端（接单 / 备货出餐）· 运营端（调度看板 / 运力管理，`/ops`）· **骑手端（任务接单 / 导航 / 位置心跳，`/rider`，移动优先）**。
- **依赖服务 / 外部依赖**：TRADE（订单/结算关联）、CRED（骑手信用档案，复用 A-06/F-03 思路）、SETTLE（分账/退款，复用 I-04 分账反向）、GPS（手机定位，前端直连，同 F-02）、**地图开放平台（高德——按车型唤起导航，E_BIKE=骑行 / CAR=驾车，H5 内嵌地图兜底；Key 由前端环境变量管理）**。
- **核心状态机**：配送订单（待支付 → 待接单 → 商户备货 → 待取货 → 配送中 → 已送达 → 已完成；分支：取消 / 超时 / 异常）。

## 2. 背景条件

- **需求背景（解决什么问题）**：消费者需「同城即时送达」（外卖/生鲜/商超），缺下单与定位选点能力；配送过程不可见、状态不透明、异常无感知（PRD §5.14 L 组）。
- **前置条件（本服务运行前提）**：
  - 消费者已实名；商品/商家支持配送；
  - 位置数据最小化使用、脱敏存储（R-03/R-07）。
- **平台红线约束（本服务需强落地）**：
  - 复用 SETTLE 结算 + P-02 存证，**不重复建结算/存证体系**（与 TRADE、SETTLE、CRED 关联）；
  - 不做北斗硬件对接——位置/轨迹复用手机 GPS（同 F-02）；
  - R-03 位置/轨迹分级授权（本人可见 → 授权可见 → 脱敏公示）。
- **里程碑边界**：M2 交付；骑手端（D-01~D-03 页面 + 骑手接口）M2 交付、设计先行（2026-09-11 调整，此前为「骑手端后置」）。

## 3. 主要功能

### 3.1 配送下单与地址定位选点（L-01）

下单选/新增收货地址（GPS 定位 + 地图选点 + 常用地址/地址簿）；校验配送范围（超范围显式提示不可达并禁用提交）；生成配送订单并计算配送费/预计送达。

### 3.2 配送订单状态机与全程跟踪（L-02）

配送订单状态机（待支付→待接单→商户备货→待取货→配送中→已送达→已完成；分支：取消/超时/异常）；消费者实时查看状态、骑手位置与轨迹、预计送达；超时/异常自动提示并可催单/投诉。

### 3.3 商家接单与备货出餐（L-03）

商户接收配送订单（接单/拒单，超时自动处理并预警）；备货/出餐状态上报（备货中→待取货）；请求取货/转运营调度；拒单原因留痕计入信用（A-07）。

### 3.4 运营调度看板（L-04）

运营端订单总览 + 地图看板（订单热力/骑手位置）；**人工派单（按车型/距离/负载简单筛选辅助，配送非即时、不引入派单算法）**、改派、取消、催单；超时/异常订单预警并人工处置；处置留痕可审计。

### 3.5 运力管理（L-05）

骑手/配送员实名、健康证、背景核验（复用 A-06/F-03 思路）、信用档案（接单履约率/超时/投诉）、在线状态、停用/启用，以及**车辆类型（电动车 E_BIKE / 汽车 CAR）/车牌/载重容积档案（L-07）**；骑手可在骑手端 D-03 切换车型、维护车辆信息，运营端 O-04 管理档案。

### 3.6 位置轨迹存证与异常预警（L-06）

配送全程位置轨迹存证（时间戳+哈希，复用 P-02）；超时/偏航/异常停留自动预警并推送运营端；轨迹可出证供纠纷仲裁（复用 D-02/T-15 机制）。数据源 = 骑手端位置心跳（`POST /delivery/rider/location`），由服务端异步写入存证链。

### 3.7 骑手端任务与双导航（L-07/L-08）

- **骑手任务（D-01/D-02）**：待接任务（READY，按车型匹配分发）与进行中任务（DELIVERING）列表；接单时校验车型/载重满足运单要求（大件货需汽车，不满足 → 3007「车型不匹配」）；取货/送达一键上报（GPS 围栏校验，未到指定地点 → 3007）。
- **双导航**：「导航到商铺（取货）」与「导航到配送地点（送货）」双按钮——由任务详情返回取货点/配送点坐标，骑手端按**车型**唤起地图开放平台导航（电动车=骑行、汽车=驾车），H5 内嵌地图兜底。
- **车型与大件兼容（L-07）**：车辆类型不限于电动车——**E_BIKE（电动车，常规小件）/ CAR（汽车，可运输大型货物）**两种车型全流程兼容（下单货件规格/派单匹配/接单校验/导航模式/调度看板车型筛选）；运单携带货件规格（常规/大件 + 重量/体积）与车型要求，汽车承担大件运输场景。

### 3.8 骑手实时位置共享（L-08）

骑手端配送中后台位置心跳（30s~60s★，Redis `rider:loc`）→ **购买的人（下单买家）在 S-31 详情页实时查看骑手位置**（SSE + 5s 短轮询兜底★，R-03 授权可见级——仅配送中可见、送达即切断）；运营调度看板 O-03 同步展示；轨迹异步入存证链（L-06）。

## 4. 非功能性需求要求

### 4.1 全平台通用基线（所有服务共同遵守）

- **规模**：覆盖 ≈840 万；注册 ≥600 万、MAU ≥200 万、商户/机构 ≥10 万、DAU 峰值 ≈120 万。
- **性能**：核心读首屏 P95 ≤2s；核心写 P95 ≤3s；API P95 ≤500ms / P99 ≤1s。
- **可用性分级 SLO**：L1 ≥99.95% / L2 ≥99.9% / L3 ≥99.5%。
- **容灾**：同城双活 + 异地灾备，RPO ≤15min、RTO ≤30min（L1）。
- **安全**：等保三级 + OWASP ASVS L2；TLS 1.2+；密钥 KMS/HSM。
- **数据**：审计日志 ≥6 个月；存证只增不改。

### 4.2 本服务专项要求

- **可用性等级：L2（≥99.9%）**——配送属 L2 覆盖对象（非核心资金链路）。
- **实时跟踪**：订单状态/位置实时推送走 SSE（5s 短轮询兜底★）；轨迹抽稀（Douglas-Peucker，10m / 每段 200 点★）+ 分段加载，降低带宽。
- **骑手端页面简洁原则**：一屏一个主操作、底部单一主按钮、大字大间距（户外骑行/驾车场景单手可操作）；任务列表只展示关键字段（取货点/配送点/预计送达/车型要求）。
- **派单一致性**：同一骑手并发派单/接单 → 幂等/乐观锁拦截，提示「已改派，请刷新」。
- **数据合规**：位置/轨迹按 R-03 分级授权——**骑手实时位置仅配送中对下单买家授权可见、送达即切断**；敏感个人信息加密存储（R-07，含车牌号）；轨迹存证只增不改（P-02）。
- **可观测**：履约率 / 超时率 / 位置心跳丢失率作为业务级监控指标。
