# 监管看板服务（DASH · Dashboard）

> 微服务说明文档 · 依据《产品需求文档》（PRD v2.0）与《产品设计文档》（PDD v1.12）编写
> 本文档用于明确该微服务的**功能与质量基线**，支持后续扩展开发。功能口径以 PDD §5.10 / §6.4.9 为准，需求口径以 PRD §5.2（A 组 A4）与 §5.1（P 组 P-01）为准。

## 1. 服务概述

- **服务标识**：`dash`（监管看板服务）
- **服务定位**：三端数据看板、**预警双向推送**与**费率 / 抽成公开公示**，实现从「事后抽查」到「数据驱动」。
- **对应模块**：A4 监管预警 / AC-M1.10 费率公示（A-08 / P-01）；P-07 民生消费券【M2，§5.14】。
- **里程碑**：费率公示页 M1、预警双向推送 M2（设计先行）。
- **实现载体 / 技术栈**：Java 17 + Spring Boot 3.5（模块化单体）。
- **三端分布**：消费端（费率 / 抽成公开）· 经营端（资质临期提醒 / 费率公开）· 监管端（预警看板 / 分级监管 / 公示核验）· 运营端（消费券运营 / 运营看板）。
- **依赖服务 / 外部依赖**：各服务（数据聚合）、MQ（通知）、CRED（证照有效期）、TICKET（举报数据）、PROFILE（商铺画像，分级监管）。
- **核心状态机**：预警双向推送（定时扫描证照 / 资质有效期 → 临期 ≤30 天或已过期 → 监管端预警看板 + 商户端提醒；违规入场高频举报聚合 → 场所预警）。

## 2. 背景条件

- **需求背景（解决什么问题）**：监管「人手不足、事后监管为主、数据不互通」（监管端 #1/#3）、经营端「抽成高获客贵」（经营端 #1）。看板用数据预警 + 分级监管把有限人力放在高风险对象上，费率公开让经营成本可预期。
- **前置条件（本服务运行前提）**：
  - 存在预警触发（每日扫描 / 举报聚合）；监管人员登录看板。
- **平台红线约束（本服务需强落地）**：
  - 预警只推送线索、**不自动执法**，人工复核后处置（C8）；
  - R-13 费率 / 抽成口径与调整规则透明、调整前提前告知（P-01）；
  - R-03 公示核验脱敏。
- **里程碑边界**：M1 交付费率公示页 + 预警基础（商户端证照临期提醒）；M2 交付双向推送完整版（A4）。

## 3. 主要功能

### 3.1 费率 / 抽成公开公示页

对外公示服务费率（0.5%~1% 分品类）与货运抽成口径、调整规则，调整前提前告知；不做竞价广告 / 隐性扣费。

### 3.2 监管预警与分级监管【M1 基础 / M2 完整】

高频投诉 / 资质临期 / 异常经营自动预警推送，按「画像风险 + 信用」双维度分级监管（低分多查 / 高分少查）；商户更新资质自动销警、处置留痕。

## 4. 非功能性需求要求

### 4.1 全平台通用基线（所有服务共同遵守）

- **规模**：覆盖 ≈840 万；注册 ≥600 万、MAU ≥200 万、商户/机构 ≥10 万、DAU 峰值 ≈120 万。
- **性能**：核心读首屏 P95 ≤2s；核心写 P95 ≤3s；API P95 ≤500ms / P99 ≤1s。
- **可用性分级 SLO**：L1 ≥99.95% / L2 ≥99.9% / L3 ≥99.5%。
- **容灾**：同城双活 + 异地灾备，RPO ≤15min、RTO ≤30min（L1）。
- **安全**：等保三级 + OWASP ASVS L2；TLS 1.2+；密钥 KMS/HSM。
- **数据**：审计日志 ≥6 个月；存证只增不改。

### 4.2 本服务专项要求

- **可用性等级：L2（≥99.9%）**——看板 / 预警属 L2 覆盖对象。
- **聚合读性能**：看板聚合多服务数据，读路径需多级缓存与只读副本；分级监管列表分页 + 筛选。
- **异步通知**：预警推送走 MQ，商户端提醒落「方便 / 惠民」两词；通知失败 MQ 重试 + 站内信兜底。
- **数据合规**：公示数据脱敏（R-03）；预警只推送线索、不自动定责（C8）。
- **可观测**：预警准确率作为业务级监控指标（PDD §8.5.3）。
