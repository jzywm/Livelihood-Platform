## 1. 范围界定与总体策略

### 1.1 域边界（ACC 测什么）

accounts-funds 域（PRD I 组）跨 ACC / SETTLE / EMP 三个服务。**本方案测试主体为 ACC**：

| ACC 承担（本方案全覆盖） | 不在本方案（边界说明） |
|---|---|
| 实名注册/回传回调/状态机（I-01，含 R-02 唯一口径） | I-02 劳务互评（EMP，ACC 不承担） |
| 钱包记账流水与汇总（I-01，纯记账簿 R-01、哈希链 R-04） | I-03 代付执行/欠薪预警/证据出证（SETTLE） |
| 收款账户绑定（I-01） | 平台结算账户对接（SETTLE，M0 对接层） |
| 人机验证 captcha（G-01 页面码，Redis） | 上述 SETTLE 能力仅以「域级集成」（§4 IT-03）覆盖 ACC↔SETTLE 协作 |
| 监管对账/资金流水审计（I-01） | — |
| 账号注销（软关闭留痕） | — |
| 强实名增强 I-06（NFC，M2） | — |

### 1.2 测试分层与环境

```
层 1 本地单测      JUnit5 + Testcontainers(MySQL8/Redis)         每次提交（G0/G1）
层 2 集成环境      SpringBootTest + WireMock(第三方 mock)        每次 MR（G2 门禁）
层 3 预发压测      双实例 + MySQL 主从 + Redis 哨兵 + JMeter      提测/上线前
层 4 生产冒烟      只读探测 + traceId 抽样核对                   每次发布后
```

测试金字塔目标配比：单元 ≈70% / 集成 ≈20% / 接口(E2E) ≈10%。

## 2. 单元测试方案

### 2.1 测试目标

在最小隔离单元锁定核心业务规则、状态机、分表路由、幂等、加密与哈希链的正确性；三条红线（R-01/R-02/R-04）以测试兜底；达到覆盖率门禁（§1.4）。

### 2.2 测试范围

① 核心业务逻辑（6 组：实名/记账/绑定/对账/人机验证/基础设施）；② 数据访问层（Mapper/DAO、SQL、唯一索引、库层权限）；③ 边界条件与异常路径（横切）。

### 2.3 测试方法

- 业务逻辑：Mockito 纯单测（领域服务/状态机/工具类）；哈希链、金额精度用 jqwik 属性测试批量生成语料验证不变量。
- 数据访问层：Testcontainers 真实 MySQL 8 + Flyway 建表（12+2 张月表），验证 SQL、唯一索引、分表路由、只增不改的库层权限。
- 边界/异常：参数化测试 + 异常断言 + `@Transactional` 回滚断言（失败后无残留行）。

### 2.4 数据准备

构造合规假数据（见 §8 规范）：合法格式但非真实的证件号（自算校验位）、测试号段手机号、金额语料、UTC/Asia-Shanghai 月末边界时间、open_id/bizId 幂等语料、WireMock 通道桩。

### 2.6 边界条件与异常路径（横切清单）

- **金额**：0、0.01、最大 decimal(18,2)、负数、超精度、科学计数法字符串。
- **分页**：page=0/负数、pageSize=0/101/超深分页；默认 page=1、pageSize=20、上限 100。
- **日期**：from>to、跨月/跨年、2 月 28/29、UTC 存储 / Asia-Shanghai 输出的时区一致性。
- **字符串**：open_id 64 上限、mobile 格式、bizId/bindingId 不存在 → 3006、业务号前缀校验（rz_/bnd_/rec_/cap_）。
- **异常路径**：第三方实名 4001 / 通道 4002 / DB 5001 / 依赖超时熔断 5002；事务半程失败回滚无残留脏数据。

### 2.7 预期结果

全部用例与上表「预期结果」列一致；错误码口径对齐 `services/_common/openapi.yaml`（0/1xxx/2xxx/3xxx/4xxx/5xxx 分段）。

### 2.8 通过标准

- 全绿无跳过（`@Disabled` 需评审理由并登记）。
- 覆盖率：行/函数 ≥80%、分支 ≥75%；核心域（实名/记账/绑定）≥90%。
- 红线用例（R-01/R-02/R-04）必测齐全，缺失即阻断合并。
- 断言有效性：PR 评审 Checklist「测试是有效断言，不是空跑/只测 happy path」。

## 3. 高并发测试方案

### 3.1 测试目标

验证 ACC 在试点峰值（平台口径：读 ≤5 千 QPS、写 ≤1 千 TPS，压测 3x；规划峰值 1.5x）下的并发读写正确性、数据一致性、性能与资源水位，定位分表路由/连接池/锁/GC 热点（对齐《高并发架构演进设计》§5、AC-NFR-6/7）。

### 3.2 测试范围

注册+回调链路、流水并发读写（跨 12 月表）、绑定/幂等并发、captcha 限流、对账触发、分布式 ID、混合场景、限流熔断、soak 稳定性。

### 3.3 测试方法

JMeter 5.6 分布式压测 + WireMock mock 实名/支付通道（第三方 mock + 真实双轨，对齐高并发 §5.2）；Prometheus + Grafana 实时监控（CPU/内存/GC/HikariCP/Redis 内存/主从延迟）；SkyWalking traceId 采样排障；压测后运行一致性校验脚本（验链、幂等审计、对账 diff、分表均衡）。

### 3.4 数据准备（建议初值，★ 压测标定）

- `account` 10 万（★）、`wallet_flow` 12 张月表共 3600 万行（★，每账户月均 30 条，触及分片阈值观察）、`wallet_binding` 10 万、captcha 挑战 Redis 预热。
- 热点账户 20% 承担 80% 流量的二八分布语料。
- 批量预灌脚本 + 灌数后备份快照（每轮压测可重置）；压测库 schema 前缀隔离。

### 3.5 场景集

| ID | 场景 | 并发模型 | 关键断言 |
|---|---|---|---|
| PERF-01 | 并发注册+回调全链路（mock 通道） | 500 并发注册 → 回调 → 状态轮询 | 无重复账户/record；TPS、P95 达标 |
| PERF-02 | 同 open_id 并发幂等轰炸 | 同一 open_id 50 并发回传 | 仅 1 账户、1 条 REALNAMED；其余全部幂等返回原账户 |
| PERF-03 | 流水并发写（created_at 随机跨 12 月） | 写 1k TPS 起、3x 加压 | 分表路由零错表；`uk_channel_order_no` 无冲突泄漏；哈希链连续 |
| PERF-04 | 流水查询（热点账户 + 冷账户 + 跨月 + 无日期默认 12 表） | 读 5k QPS 起、3x 加压 | P95 ≤500ms / P99 ≤1s；分页不重不漏 |
| PERF-05 | 汇总接口高频（wallet/summary） | 与 PERF-04 并行 | 聚合走从库/异步，不拖垮 OLTP 主库 |
| PERF-06 | 绑定并发（同 account+channel / 异账号混合） | 200 并发 | 同键仅 1 行 BOUND；Idempotency-Key 全部返回首次结果 |
| PERF-07 | captcha 下发 + verify 并发 | 500 并发下发、高频 verify | 一次性消费 100% 生效；爆破触发 429；Redis 内存无异常增长 |
| PERF-08 | 对账并发触发（同/异 Idempotency-Key） | 100 并发 | 同键单任务；对账走异步/从库不压 OLTP |
| PERF-09 | 分布式 ID 双实例并发写 | 双实例 × 1000 线程 × 10 万次 | 0 重复 ID；workerId 无撞车 |
| PERF-10 | 混合场景：读 90% + 写 10% 全链路 | 对齐平台口径 | 全链路达标、无级联劣化 |
| PERF-11 | 限流熔断：读 1000 req/s/账号、写 100 req/s/账号 | 超限流量 | 429 行为正确、不误伤正常流量、不雪崩 |
| PERF-12 | Soak：持续 30min 混合负载 | 峰值 70% 水位 | 无内存/连接泄漏、无死锁、无 GC 风暴 |

### 3.6 数据一致性专项（压测后校验）

| 校验 | 方法 | 通过标准 |
|---|---|---|
| 幂等一致性 | 审计重复请求响应 | 100% 返回首次结果（code/数据一致） |
| 哈希链完整性 | 全量/抽样重算验链 | 100% 链连续、无断链 |
| 写后立即读 | 绑定/注销后立即查询 | 读到新状态（强制主库，无主从延迟脏读） |
| 主从分离 | 模拟从库延迟 | 关键资金读走主库；普通读容忍延迟 |
| 对账一致性 | 平台流水 vs mock 通道账单 | diff=0（3009 不触发） |
| 分表均衡 | 按表统计行数 | 按月分布均匀，无单表热点 |
