## 关键决策与理由

- 首选 `dsh-code-intel` 而非 `dsh-context-milvus`：前者无需额外中间件、索引落在工作区 `.dsh/code-index/` 跨会话复用，直接命中「避免重读大文件」；后者语义检索更强但需自建 Milvus，上手成本高
- 安装优先 Release tarball 预构建（`dsh plugin --profile web add <release .tgz URL>`）→ 免 pnpm 10+ 的 build 白名单；README 自述 npm 未 live，但 npmmirror 实测已有 0.1.3

## 经验与教训

- **沙箱网络边界（可复用）**：`find_dsh_plugin` / `raw.githubusercontent.com` 直连在当前沙箱不可达（TLS 拦截）；但 npm 走 `registry.npmmirror.com` 镜像可达，写全局 npm-cache 被 EPERM 拒绝 → `--cache` 指向工作区目录解决；`web_search` 是唯一稳定外网工具
- **插件「已装未用」盲区**：DSH 插件装在 `<DSH_HOME>\profiles\<profile>\node_modules`，是否生效由 profile `package.json` 的 `dsh.profile.bundles` 决定——用户此前不知已装，排查时先看 bundle 列表与 `dist` 源码最快
- 插件只「提供并推荐」code_search/code_outline，不强制禁止 `read` → 稳定不重读大文件还需 Agent 行为配合（系统提示已注入优先用索引的指引）
