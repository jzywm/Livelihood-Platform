# 设计说明：implement-aicore-service

## Context

动机见 `proposal.md` - Why。本设计只记录影响实现方式的现状约束：

- **现状**：`services/aicore/` 只有 4 份文档（README / `openapi.yaml` v1.1.0 / `er.md` v1.2 / apifox 产物），无任何代码。`er.md` v1.2 已定档 9 张表结构与分表口径，`openapi.yaml` v1.1.0 已定档 M1 的 2 个前端接口与 3 个服务端间接口（含习惯计算）。两者是本变更的**接口与库表唯一可手改源**，实现不得反向改文档来迁就代码。
- **调用方现状**：GATEWAY 已预留 `id: aicore` 路由（`uri: http://localhost:8083`、`Path=/api/v1/aicore/**`、`RewritePath=/api/v1/(?<segment>.*), /$\{segment}`、`metadata.timeout: 5000`）与 `Tier.AI`（10 次/分/账号），但路由处于注释状态；GATEWAY 只做网关级限流与鉴权，域级配额与成本预算属 AICORE 自身职责。PROFILE 侧已定档习惯计算调用链与三张表，等本服务提供接口。
- **技术约束**：AI 侧固定 Python 3.12 + FastAPI（PDD §3）；关系库固定 MySQL 8 且**不引入其他关系库引擎**（config context、PDD §4.4）；ASSIST 是另一个 Python + FastAPI 服务，本服务的分层与 Provider 抽象将作为其参照，故本次分层要一次做对。
- **红线约束**：R-05/C8（AI 只标记不决策）、R-03（数据分级授权）、R-07（画像不杀熟）在代码层需要**工程化强制**而非仅靠约定——这是本设计与普通微服务的最大差别。
- **环境约束**：沙箱与 CI 无真实模型密钥、不应产生调用费用，测试必须可离线运行。
- **范围**：仅 M1（K-02 网关底座 + K-01 证照 OCR + 合规/成本护栏 + 习惯无状态计算）；K-03/K-04/K-05/K-06 只留扩展位。

## Goals / Non-Goals

**Goals：**

- 让 M1 的 AI 能力**真正可运行**：OCR 可从上传走到可追溯结果，习惯计算可被 PROFILE 真实调用。
- **红线可验证**：C8「无人工结论不得回写」、R-05「不回流第三方」、R-07「权重不进定价」都由代码结构 + 自动化用例兜住，不依赖人工自觉。
- **可离线测试**：模型通道可替换，CI 无密钥、零费用即可跑完整单测。
- **可演进**：M2 的视觉审核 / 图像问答、M3 的风险预测不改动 M1 已定的接口契约与任务模型，只新增通道与任务类型。
- 为 ASSIST 与后续 Python 服务提供可复用的工程基线（分层、Provider 抽象、可观测、错误码）。

**Non-Goals：**

- 不实现 K-03/K-04/K-05/K-06 的业务逻辑（只保留任务类型枚举与通道路由扩展位）。
- 不接 SkyWalking Python agent、不建 Grafana 看板、不建 CI 流水线（平台级变更统一做）。
- 不做模型微调或第三方训练回流（R-05/C8 明令禁止）。
- 不把 AI 网关做成接入层网关——`/api/v1/aicore/**` 的鉴权、限流、traceId 注入仍由 GATEWAY 承担；AICORE 只管域内配额与成本。
- 不引入 PostgreSQL、不引入新的消息中间件（理由见 D2）。

## Decisions

### D1：Python 3.12 + FastAPI + Pydantic v2，分层为 api / service / provider / repository / core

**选择**：按 `api`（路由与 DTO 校验）/ `service`（业务编排）/ `provider`（模型通道，外部依赖边界）/ `repository`（MySQL 访问）/ `core`（配置、日志、错误码、鉴权、限流、可观测）分层，DTO 用 Pydantic v2。

**为什么**：PDD §3 已定档 Python + FastAPI，无选型空间。分层的真正理由是本服务有**两类不可混淆的边界**：Provider 是对外调用边界（决定合规与成本），repository 是自有库边界（决定数据归属）。把两者分开，才能让「脱敏前置」「不回流第三方」这类约束落在单一位置可审计。

**已考虑的备选**：① 扁平结构（`main.py` + 少量模块）——M1 功能少时更快，但 M2 加视觉审核后会迅速退化，且合规检查点会散落；② Django REST Framework——ORM 与 admin 更方便，但异步任务与 asyncio 并发支持弱于 FastAPI，且与 ASSIST 既定栈不一致。均否。

### D2：异步任务用「MySQL 任务表为事实源 + Redis 原子领取」的多实例安全队列，不引入 RabbitMQ

**选择**：`ai_task` 表（对齐 `er.md` §7）作为任务的唯一事实源。提交即写库返回 `taskId`；执行侧由工作协程经 Redis 的原子操作领取任务（`SET NX` 租约 + 超时回收），同库可多实例并行且不重复执行。进度与结果写回 `ai_task` 与结果表，前端与调用方经 `GET /aicore/tasks/{taskId}` 轮询。

**为什么**：① 并发量极低——AI 任务量受**业务动作数**限制（上传证照 / 提交审核），量级约 1 万次/日，折算远低于 1 QPS，用消息中间件属于杀鸡用牛刀；② 任务状态本来就必须落库（`er.md` §7 `ai_task.status/progress` 是接口契约的一部分），再用 MQ 会造成「MQ 与 MySQL 双事实源」的一致性问题——必须额外处理「MQ 已消费但库未更新」「库已更新但 MQ 重投」两类不一致；③ 不新增中间件就少一个高可用组件（RabbitMQ 的 Erlang 运行时与集群运维成本对 M1 不划算）。

**已考虑的备选**：① RabbitMQ（平台已选型）——M2 任务量上升或需要与主站统一削峰时再切；当前引入会让 M1 多一个必须高可用却低负载的组件；② FastAPI `BackgroundTasks` 进程内执行——实现最简，但进程重启即丢任务、多实例无法协同，不符合「任务可查询、可对账」的契约；③ Celery——需要 broker（回到 ②/① 的问题）且依赖较重。均否。

**可演进性**：领取逻辑收敛在 `core/task_runner`，M2 若切 MQ，只需替换领取实现，`ai_task` 表仍是事实源，接口与调用方零改动。

### D3：模型通道抽象为 Provider Protocol，Mock 为开发/测试默认，生产禁用 Mock 且启动即校验

**选择**：`provider/` 定义 TextProvider / VisionProvider / OcrProvider 三个 Protocol（结构子类型，不强制继承）。实现 `mock`（确定性、可离线）与真实实现骨架（DeepSeek 文本、云视觉、云 OCR）。Provider 由配置选择，**默认 `mock`**。当 `env=prod` 而选中 `mock` 时，**进程启动失败并输出阻断级日志**，不允许静默降级。

**为什么**：① 测试必须离线——真实模型调用需要密钥与预算，且图像样本涉及合规，不能让 CI 依赖；② 「密钥缺失时自动降级 Mock」在开发环境很便利，但**在生产环境自动降级 Mock 会造成更严重的合规事故**（等于用假数据伪造 AI 结论并进入人工复核），因此必须区分环境：dev/test 允许降级并告警，prod 直接拒绝启动；③ 契约测试可针对 Protocol 编写，真实实现与 Mock 跑同一套用例，避免「Mock 通过、真实实现不兼容」。

**已考虑的备选**：① 直接接真实 API + 录制回放（VCR）——更贴近真实行为，但首次录制仍需密钥与预算，且回放数据会含证件图像等敏感内容，存档本身有合规风险；② 只留接口不实现——交付物不算可用，M1 验收项 AC-M1.11 无法取证。均否。

### D4：图像脱敏作为不可跳过的前置阶段，脱敏失败即拒绝外发

**选择**：Provider 调用前必经 `service/desensitize` 阶段（人脸 / 车牌检测后区域覆盖或不可逆处理）。该阶段产出脱敏后对象并**不回写原图**；若脱敏失败或超时，任务直接转人工复核（`4003` / `MANUAL_REVIEW`），**不得以「脱敏失败但先发出去」的方式继续**。

**为什么**：R-03/R-05 要求图像脱敏前置。工程上最容易出错的地方是「脱敏失败时为了不阻塞业务而放行」——这在代码里表现为一个 try/except 的降级分支。本决策把它明确为**失败即拒绝**，并在用例中固定该行为，使合规边界不随开发便利性漂移。

**已考虑的备选**：① 由前端上传时脱敏——前端不可信（可绕过），且无法审计；② 交给云视觉 API 侧脱敏——数据已经出域，红线不满足。均否。

### D5：C8 以「状态机 + 数据库约束」双重强制，不靠业务代码自觉

**选择**：`review_verdict.authority_written` 默认 `false`；触发权威回写的前提是**已存在人工复核结论**（`review_verdict` 有行且 `action` 为人工结论）。回写成功后写 `authority_written=true` 与 `authority_event_id`，事件标识作为消费方幂等键；每日对账按 `authority_written=true` 与消费方回执比对差异并告警。AI 产出的标记**没有**任何直接写权威数据的代码路径。

**为什么**：「AI 只标记不决策」如果只写成一句注释，迟早会被某次「紧急需求」绕开。因此本设计把决策点收敛为**一个字段的状态转移**：没有人工结论行，就没有回写入口。对账则解决「回写发出但消费方未生效」的静默失败。

**已考虑的备选**：① 代码评审 + 注释约定——无强制力，不可测试；② 数据库触发器强制——触发器逻辑对应用不可见、难测试、难迁移，且跨库回写本就无法用触发器表达。均否。

### D6：成本护栏分三层，且与网关限流职责不重叠

**选择**：① 单账号日配额（Redis 计数，超限业务码 `2004`）；② 全局日预算（Redis 计数 + 阈值：80% 告警、100% 降级为人工复核路径）；③ 成本按调用方归因（每次调用记调用方与 token / 次数量，可周期出账）。两层限流并存且职责不同：**GATEWAY 的 10 次/分/账号是防滥用的速率限制，AICORE 的日配额与预算是成本上限**。

**为什么**：只是限速不能控成本（10 次/分持续一天也是天量调用），只控总量不能防瞬时打爆。二者正交，必须都有。此外**服务端间接口（习惯计算）不计入账号级档位**——它没有终端账号语义，按调用方服务身份单独归因。

### D7：习惯计算为无状态纯函数，结论置信度独立于样本量口径

**选择**：计算实现为纯函数 `(agg, windowDays, minSampleCount) -> (habits, factors, is_empty, model_meta)`，**无任何写库路径**。滚动窗口 90 天（可覆盖）、时序衰减按分桶衰减（新证据权重高于旧证据）；样本量低于 `minSampleCount`（默认 20）返回 `isEmpty=true` 与空数组，而非降置信度硬出结论。输出只含权重 / 样本量 / 可读证据，**不含人格推断标签**；`model_meta` 回执算法版本、窗口天数、最小样本量与阈值快照。

**为什么**：① 无状态是「权威存储归 PROFILE」这一边界决策（SSOT v2.0 §4.16-C16）在代码上的必然形态——纯函数使算法迭代不触发数据迁移；② 「样本不足返回空」而非「低置信度硬出」很重要：低置信度结论一旦落库，下游排序无法区分「弱证据」与「无证据」，不如显式留空；③ R-07 要求不杀熟，结构上保证权重只参与排序即可——本条由 D8 的用例固化。

**已考虑的备选**：① 在本服务缓存中间结果以加速重算——会立刻变成事实上的长期记忆存储，违背边界决策；② 返回人格标签（如「价格敏感型」）——属人格推断，合规风险高且不可解释。均否。

### D8：R-07「权重不进定价」以用例固化，而非仅在文档声明

**选择**：新增一条针对性用例：给定同一商品与两个权重差异极大的画像，断言最终价格字段完全一致、且权重只出现在排序相关调用路径中；同时对排序链路做「不引用价格字段」的结构性断言。

**为什么**：R-07 的失效方式是「某次为了转化率把权重接进定价」，属于渐进式越界。用一个会变红的用例把它钉住，比在文档里写一句「不得杀熟」有效。

### D9：可观测性「齐备但不铺满」

**选择**：`/health`（存活）与 `/health/ready`（依赖就绪）分离；结构化 JSON 日志与主站同 schema（含 traceId）；traceId 从 GATEWAY 注入的请求头透传至所有下游调用与日志；Prometheus 指标暴露 OCR 通过率、任务成功率、任务耗时分布、人工复核量 / 总调用量（准确率主指标）、配额与预算水位。**不做**：SkyWalking Python agent 接入、Grafana 看板、告警规则。

**为什么**：M1 验收项 AC-M1.11 与 NFR「AI 类同步 P95 ≤3s」需要可取证的数据，故指标必须做；而链路追踪后端与看板属平台级能力，本服务先保证按标准格式输出，接入留给平台级变更，避免被外部进度阻塞。

### D10：GATEWAY 路由启用，但不在 AICORE 侧重复鉴权逻辑

**选择**：放开 GATEWAY 中 `id: aicore` 路由（放开即可，`RewritePath` 已把 `/api/v1/aicore/**` 去前缀，故 AICORE 侧路由路径为 `/aicore/**`，与 `openapi.yaml` 一致）。终端接口的 JWT 校验、账号级限流、traceId 注入由 GATEWAY 承担；AICORE 只做**服务端间接口的内部 Token 校验**与域内配额。

**为什么**：网关是唯一鉴权点（`implement-gateway-service` 已定档），AICORE 重复实现 JWT 校验会造成两个鉴权点、责任不清。但习惯计算是服务端间调用，不携带终端 JWT，必须由 AICORE 自行校验内部凭据——这是两个不同的信任域，不能混为一谈。

### 依赖方向规则（可由检查固化，violation 即用例变红）

```
api ──→ service ──→ {provider 抽象, repository, port}
                  ↑
        core ←────┘（任何层都可用 core；core 不依赖任何业务层）
main.py（组合根）：唯一允许把具体 Provider / repository 实现注入 service 的位置
```

**禁止项**（逐条对应一条自动化检查）：

1. `api/` MUST NOT 直接导入 `repository/` 或 `provider/`——路由只调 service。
2. `service/` MUST NOT 导入任何具体 Provider 实现（`mock` / `deepseek` / `cloud_*`），只依赖 `provider/base.py` 的 Protocol。
3. `repository/` 与 `provider/` MUST NOT 导入 `service/`——否则边界倒置，合规检查点会失效。
4. `core/` MUST NOT 导入 `service/` / `provider/` / `repository/`。
5. 只有 `provider/` 下的模块可以发起外部模型 HTTP 调用（`httpx` 的模型调用仅出现在该包内）。
6. `service/desensitize.py` 与 `service/verdict.py` MUST NOT 出现「异常后继续执行」的降级分支——分别承接 D4（脱敏失败即拒绝）与 D5（无人工结论不回写）。

**为什么把规则做成检查**：本服务最容易退化的不是功能而是边界——「顺手在路由里查一下库」或「脱敏失败先放行」这类改动单看都合理，累积起来就是合规事故。规则可执行，才不会随开发便利性漂移。

## 接口分类与任务契约

| 类别 | 接口 | 是否落 `ai_task` | 语义 |
|---|---|---|---|
| 终端异步 | `POST /aicore/ocr` | 是 | 受理即返回 `taskId`，实际处理由执行器内核承接 |
| 结果轮询 | `GET /aicore/tasks/{taskId}` | 读 | 查进度与结果，仅限提交者本人（跨账号 `2002`） |
| 服务端间同步 | `POST /aicore/habit/summarize` | **否** | 纯计算，同步返回、无副作用、不产生任务与进度语义 |

**习惯计算为什么不落任务表**：① 它是纯函数计算（D7），落库只会让「只算不存」的边界变脏；② `ai_task` 的分表键是 `(account_id, created_at)`，而该接口按 `accountId` + `periodEnd` 幂等重算，套进任务模型会引入与需求无关的状态机；③ 它无进度可报——计算耗时远低于轮询成本，异步化只会增加调用方的复杂度。异常仍按统一错误码返回（越权 `2002`、依赖超时 `5002`）。

**任务类型策略注册表**：`ai_task.type` 的每个取值对应一个处理器，在 `service/task/registry.py` 注册，处理器需声明自身的结果结构、超时与是否可重试：

| 任务类型 | 处理器 | 结果结构 | M1 是否实现 |
|---|---|---|---|
| `OCR` | `service/ocr_service.py` | `OcrResult` | 是 |
| `VISION_REVIEW` | 预留注册位 | `VisionReviewResult` | 否（M2） |
| `KITCHEN_ANOMALY` | 预留注册位 | `KitchenAnomalyResult` | 否（M2/M3） |
| `RISK_PREDICT` | 预留注册位 | `RiskPredictResult` | 否（M3） |

**为什么用注册表**：M2 新增视觉审核时，期望的改动量是「新增一个处理器文件 + 一行注册」，而不是去改 `task_runner` 的分支逻辑。这也保证 `task_runner` 在 M1 之后保持稳定——它是 D2「M2 可切 MQ」的替换点，越少人动越好。未注册的类型必须显式失败（而非静默忽略），避免告警丢失。

## 异步并发与任务执行器内核

**并发模型**：单事件循环 + 受控线程池，边界明确如下。

| 工作类型 | 执行位置 | 理由 |
|---|---|---|
| HTTP 路由处理、Redis 操作、出向 HTTP 调用 | 事件循环（`async def`） | I/O 等待型，异步最划算 |
| MySQL 访问 | 线程池（同步 SQLAlchemy 会话） | 见下「数据层落地」 |
| 图像解码、脱敏处理、哈希与存证计算 | 线程池（`run_in_executor`） | CPU 密集，留在事件循环会阻塞全服务 |

**为什么 CPU 密集必须下线程池**：图像脱敏是 M1 最重的计算（解码 + 检测 + 重绘）。若在协程内直接调用，一次脱敏就会卡住整个事件循环，使同一实例上所有任务受理与轮询一起变慢——表现为「并发数不高但 P95 爆表」。这条同时是 NFR「AI 类 P95 ≤3s」能否守住的前提，故必须显式定档并有用例约束（断言重活不在事件循环内执行）。

**任务领取的原子性**：以 `ai_task` 为事实源，Redis 提供原子领取与租约——`SET key value NX PX <leaseMs>`；租约到期未被续期即可被其他实例回收，续期由心跳完成。**续期失败必须主动放弃任务**而非继续执行，避免出现「两个实例同时处理同一任务」的重复外部调用（会产生真实费用与重复标记）。

**重试与退避**：失败按指数退避重试，超过最大次数置 `FAILED` 并转人工复核队列（对应用例：不静默丢单）。外部通道失败（`4003`）与依赖超时（`5002`）分别计数，避免把「通道挂了」误判成「任务有问题」。

**并发度与背压**：实例内并发任务数由信号量封顶（可配）；队列深度作为指标暴露，超过阈值告警以触发扩容或降级评估——这是 D2「无 MQ 吞吐上限」风险的观测手段。

## 数据层落地

**ORM 与会话**：SQLAlchemy 2.x 声明式模型（`Mapped[]` 风格，mypy 友好）。采用**同步会话 + 线程池**，而非 async driver：本服务分表需按 `(account_id, created_at)` 动态定位物理表，动态表名的 SQL 构造在同步会话下更直观，且能规避异步驱动下「会话跨事件循环使用」的经典陷阱。

**按月分表路由**：`repository/sharding.py` 实现与 Java 侧同语义的路由（`er.md` §5.3 要求）——按分片键计算物理表名 `ai_task_YYYYMM` / `ocr_result_YYYYMM` / `ocr_correction_YYYYMM`；写入前确保当月物理表存在（幂等建表）；查询 MUST 携带分片键下推，**禁止跨分片 JOIN 与聚合、禁止跨分片事务**。跨月统计走异步导出而非在线联表。

**Schema 迁移**：Alembic 管理版本化迁移；分表物理表的创建无法用普通迁移表达，改由幂等建表脚本 + 迁移钩子承接，迁移脚本与 DDL 同放 `deploy/sql/`，遵循 expand-migrate-contract（`er.md` §5.6）。**禁止手改线上库结构**。

**与 `er.md` 的一致性**：以 `information_schema` 导出实际库表结构与 `er.md` §6 数据字典做自动比对，任一侧单边改动都会使比对失败——防止「代码改了表、文档没跟上」或反之。

**连接池与只读副本**：写会话与只读会话来分离，池大小按实例并发度设定并从配置读取（不写死）；只读路径（如准确率统计）走副本，与写路径隔离以免统计拖慢受理。

**事务边界**：单表写入一个事务；跨表但同分片的写操作可在一个事务内；**跨分片一律拆为多次独立事务 + 幂等补偿**，不引入分布式事务。

## 跨服务出向端口与事件适配

**端口定义**（`port/`，只在 `service/` 中被依赖，实现由组合根注入）：

| 端口 | 目标 | 载荷 | 幂等键 |
|---|---|---|---|
| `CredPort.write_authority` | CRED（A-02 档案 / 信用分） | 复核结论 + 商户标识 | `authority_event_id` |
| `DashPort.report_alert` | DASH（A-08 预警） | 预警摘要 + 风险等级 | `authority_event_id` |

**为什么走端口而不是直接调 HTTP**：① D5 要求「无人工结论不得回写」——把回写能力收敛到一个端口，使「谁可以触发回写」只有一处可审计；② 端口使 M1 可以在测试中以 fake 实现零外部依赖运行（测试架构）；③ 与 D2 呼应：**若 M2 切换消息队列，只需替换该层的发送实现**，端口签名与 service 调用方不动。

**可靠性**：发送采用指数退避重试；重试耗尽进入死信记录并告警（**不静默丢弃**——丢一条回写意味着一条违规未被记录）。每日对账以 `authority_written=true` 的记录与消费方回执比对，差异可发现、可补发（D5、任务 6.3）。

**发送时机**：回写只由「人工复核结论落地」这一事件触发，MUST NOT 由 AI 产出直接触发；`authority_written` 的状态转移是唯一入口。

## 横切关注点：配置、异常、traceId

**配置（`core/config.py`）**：Pydantic Settings 模型，按 `env` 加载，分环境文件不入库。**启动即校验**，校验失败进程拒绝启动并输出阻断级日志：

1. `env=prod` 且 Provider 选中 `mock` → 拒绝启动（D3）；
2. 真实通道被选中但密钥缺失 → 拒绝启动（生产不允许以「无密钥」状态运行）；
3. `dev` / `test` 允许降级为 `mock` 并输出告警（不阻断）；
4. 数据库、Redis、配额与预算阈值等必填项缺失 → 拒绝启动，不做默认值兜底（默认值会把配置错误隐藏到运行时）。

**异常与错误码（`core/errors.py`）**：业务异常以 `AiCoreError` 为基类，子类携带错误码常量（`1001` / `1002` / `1003` 参数类、`2001` 未登录或 Token 失效、`2002` 越权、**`2004` 请求过于频繁**、`3006` 对象不存在、`4003` 通道失败、`5002` 依赖超时），由全局异常处理器统一映射为 `core/envelope.py` 的信封。**未预期异常一律归 `5000`**，不把内部异常细节写进响应体（堆栈只进日志）。业务代码只抛业务异常，不自行拼装信封——否则错误码口径会散落。

> **错误码取值一律以 `services/_common/openapi.yaml` 的 `ErrorCode` 枚举为准**（`2026-09-16` 口径校正）：
> ① 限流的**业务码是 `2004`**，不是 `429`——`429` 是 HTTP 状态码，不在平台码表内，两者不可混用（限流响应可同时给出 HTTP `429` 与业务码 `2004`）；
> ② 参数类错误必须映射为 `1001` / `1002` / `1003`——FastAPI 默认返回 `422` 与框架自有结构，若不收编，前端会拿到两套响应格式；
> ③ `2001` 用于内部 Token 校验失败（任务 10.3 要求服务端间接口不接受终端 JWT，拒绝时需有明确业务码）。
> 已核实的取值：`Envelope` 必填字段为 `code` / `message` / `traceId` / `timestamp`（`traceId` 为 camelCase、`timestamp` 为 UTC ISO 8601），**成功码为 `0`**——前端按 `code === 0` 判断成功。

**traceId（`core/trace.py`）**：中间件从 GATEWAY 注入的请求头读取并写入上下文变量；日志过滤器与出向 HTTP 客户端均从上下文取用，使「网关 → AICORE → Provider → 回写」全程可串。**网关未注入时自行生成**（而非留空），保证本服务日志始终可串联；生成行为需可在日志中区分，以免掩盖网关故障。

> **请求头与凭据口径（`2026-09-16` 校正，依据 PDD §8.5.1 L1750 与高并发 §7.6 L424）**：
> ① traceId 的注入请求头是 **`X-Request-Id`**（不是 `X-Trace-Id`），映射为信封与日志中的 `traceId`；
> ② 服务端间接口（`x-external-interfaces`）的内部凭据头名平台此前未定义，本服务定名为 **`X-Internal-Token`**，并补写进 `services/aicore/docs/openapi.yaml` 的 `securitySchemes`——该头名是 PROFILE 侧调用时必须一致的跨服务契约，不写入接口文档则两服务必然对不上；**MUST NOT 接受终端用户 JWT**（与 GATEWAY 的 `Authorization: Bearer` 属两个信任域）。

**与 D9 的衔接**：日志字段 schema 与主站保持一致（`core/logging.py` 统一产出），业务代码只传结构化字段，不手工格式化字符串。

## 测试架构与离线策略

**分层**：

| 层 | 范围 | 依赖 |
|---|---|---|
| 纯函数单测 | 习惯计算引擎、衰减、证据生成、置信度分级、类目比对 | 零依赖 |
| 契约测试 | Provider Protocol、repository 接口、port 接口 | 依赖替身 |
| 仓储测试 | 分表路由、跨月边界、幂等写入 | 内存或轻量数据库 |
| 接口测试 | 路由契约、鉴权、错误码、信封 | `httpx` ASGI 传输 + 依赖替身 |
| 端到端 | 网关 → AICORE → Provider(Mock) → MySQL | 集成标记，需真实依赖 |

**夹具（`tests/conftest.py`）**：提供配置夹具（按环境覆盖）、fake provider（确定性、可注入延迟与故障）、内存/轻量库会话、ASGI 客户端与应用装配夹具。**测试内不出现任意 sleep，等待统一走可控时钟或轮询断言**——否则跨月、租约、对账这类时间相关用例会变成不稳定测试。

**离线保证**：纯函数、契约、接口、仓储四层在**零密钥、零外部中间件**下即可跑通；只有端到端层需要真实 Redis / MySQL，并以 `@pytest.mark.integration` 标记，默认不执行。这是「默认 Mock Provider」（D3）在测试侧的对偶设计。

**覆盖率口径**：`pytest --cov` 对 `src/aicore` 统计，门禁 ≥80%（`DEVELOPMENT_CONSTRAINTS.md` 要求）。`main.py`（组合根）与 `provider/` 中的真实通道骨架允许排除——它们的正确性依赖真实外部服务，用真调用来刷覆盖率既花钱又不反映质量；真实通道以 D3 的契约测试 + 小样测评验收。

**额外两类专项测试**（非覆盖率导向，但必须存在）：

1. **结构性断言**：分层依赖规则（「依赖方向规则」6 条禁止项）、Provider 不接收纠错语料（任务 5.6）、AI 产出路径无权威回写调用（任务 6.1）、习惯计算不调用 repository（任务 8.3）、输出字段白名单（任务 8.11）。
2. **离线可跑证明**：断网或屏蔽出口流量的环境下执行四层测试必须全绿——这是 D3 与「可离线测试」目标的可验证形式。

## Risks / Trade-offs

- **[无 MQ 导致任务吞吐上限]** → M1 任务量远低于单实例 MySQL 领取吞吐；领取逻辑收敛在 `core/task_runner`，切换 MQ 只改一处，接口与事实源不变。指标上监控「任务排队时长」，超阈值即触发切换评估。
- **[进程内工作协程随实例重启丢失在途任务]** → 任务事实源在 MySQL，租约超时后由其他实例或重启后的实例回收重试；租约超时值可配，重试次数超限置 `FAILED` 并转人工，不静默丢单。
- **[脱敏能力受限于检测精度（人脸 / 车牌漏检）]** → 脱敏失败即拒绝外发（D4）；同时把「脱敏后仍含人脸 / 车牌」加入抽样人工复核检查项，作为持续发现手段。
- **[Mock Provider 与真实 Provider 行为不一致]** → 同一套 Protocol 契约用例同时跑两者；真实通道以「先小样测评再定」的方式验收（需求 29 §9 已定档），不达标不切换。
- **[人工复核只能发现误标、发现不了漏检]** → 已定档 1%~5% 未标记样本抽样复核 + 以「人工复核量 / 总调用量」为主指标；漏检率作为观察指标，不因它好看就停止抽样。
- **[成本护栏误伤正常业务]** → 80% 仅告警、100% 才降级，且降级路径是转人工而非直接失败；配额按账号而非全局，避免单账号拖累全平台。降级事件必须告警，防止预算长期触顶被当成常态。
- **[习惯计算权重被下游误用]** → 用例固化（D8）+ 结论字段不提供价格语义；PROFILE 侧的四权与合规门禁由该服务自身用例承担。
- **[PDD §6.4.13 与 openapi.yaml 路径不一致]** → 以 openapi.yaml 为唯一可手改源修正 PDD（`/vision/reviews`、`/kitchen/anomalies`），并在任务中显式列出，避免实现期按 PDD 写错路径。
- **[分层规则退化（顺手绕过边界）]** → 6 条禁止项做成自动化检查而非评审约定；尤其「api 直接查库」与「脱敏失败先放行」这两类看似合理的改动会被立即拦下。
- **[CPU 密集任务阻塞事件循环导致 P95 恶化]** → 图像脱敏与哈希计算强制走线程池，并以用具例断言重活不在事件循环执行；这条同时是 NFR「AI 类 P95 ≤3s」能否守住的前提。
- **[租约续期失败仍继续执行导致重复外部调用]** → 续期失败主动放弃任务，宁可让其他实例重做（结果幂等）也不允许两个实例同时调用付费通道；外部调用结果按任务号去重写回。
- **[同步 SQLAlchemy 会话 + 线程池的模型复杂度]** → 相比 async driver 多一层线程池管理；换来的是分表动态 SQL 直观、且规避「会话跨事件循环」陷阱。若将来只读路径成为瓶颈，可单独把统计类查询改造为异步，不影响写路径。
- **[配置默认值掩盖错误]** → 必填项缺失即拒绝启动、不兜默认值；代价是部署时配置不全就起不来，但把错误暴露在启动期远好于暴露在第一次真实调用时。
- **[端到端层默认不执行导致集成缺陷后置]** → 以 `@pytest.mark.integration` 标记并在发布前强制跑一次；日常迭代靠契约测试与依赖替身保证反馈速度，端到端作为发布门禁而非每提交门禁。
- **[`er.md` 与 DDL 单边改动]** → 自动比对 `information_schema` 与数据字典，任一侧单边改动即失败；避免「代码改了表、文档没跟上」这类静默漂移。

## Migration Plan

1. **建工程与库**：新增 `services/aicore/`（工程、配置、分层骨架、`deploy/Dockerfile`）；建库 `aicore` 并执行 `deploy/sql/**`（9 表 + 分表），不触碰主站库与其他服务库。
2. **落底座**：错误码 / Envelope / traceId / 结构化日志 / 健康检查 / 内部 Token 鉴权 / Redis 限流 / 成本护栏；此时服务可启动、可探活，但无业务接口。
3. **落任务模型**：`ai_task` 提交 - 领取 - 回执链路 + Provider Protocol + Mock 实现；`GET /aicore/tasks/{taskId}` 可用（越权 2002、幂等、状态机）。
4. **落 OCR**：`POST /aicore/ocr` + 脱敏前置 + OCR 通道 + 有效期 / 类目比对 + 失败转人工；补 `ocr_correction` 纠错回流与评估集回归。
5. **落习惯计算**：`POST /aicore/habit/summarize` 纯函数 + 内部鉴权 + 幂等 + 窗口 / 衰减 / 样本不足口径；联调 PROFILE 侧链路。
6. **接网关**：放开 `id: aicore` 路由，端到端联调 `/api/v1/aicore/**`；确认限流档位与内部调用计档方式。
