## 1. 评审清单（评审人逐项核对）

### 1.1 完整性 —— 需求是否覆盖应覆盖的范围
- [ ] P0 模块（I1/I2/I3 账户系统、A1/A2/A3/C2/D2/G1/T2+T3）均有用户故事、关键流程、数据字段
- [ ] **账户系统 I1~I5**：实名/钱包记账/劳务信用/工资代付/商品分账/零工结算均有细化（`24-平台账户系统需求.md`）
- [ ] T1~T5 均有用户故事、关键流程、数据字段、状态机、页面清单
- [ ] 扩展模块 F/G2/H/EDU 均已细化（`13-扩展模块用户故事.md`、`16-教育培训需求调研.md`）
- [ ] 10 行业 + 跨行业公共功能均有行业功能映射（规格书 §5）
- [ ] 非功能需求（合规/安全/可信/轻量/开放/结算/端形态）覆盖齐全
- [ ] 里程碑规划明确 MVP 范围、时间预期、退出标准、风险
- [ ] **对接不可接替代方案**（证照人工核验/自建工单/第三方支付通道）均已明确

### 1.2 一致性 —— 需求之间是否冲突/重复/衔接正确
- [ ] T2 供应商信用与 A3 信用分体系复用关系明确（同一主体档案贯通）
- [ ] T3 一物一码与 B1 全链溯源关系明确（T3 为 B1 的批次级升级）
- [ ] **I3 工资代付与 I4 商品分账均走第三方持牌通道，口径一致（平台不沉淀资金）**
- [ ] **I2 劳务信用与 A3/A2 信用分联动关系明确**
- [ ] T4 货款分账与 I4 商品结算衔接一致（验收后放款）
- [ ] T5 投诉直达与 D2 复用关系明确，升级路径一致
- [ ] 优先级（P0/P1/P2）与里程碑分期一致（P0→M1，P1→M2，P2→M3）
- [ ] 角色定义（六方+供应商）与各模块用户故事中的角色一致
- [ ] **对接不可接结论（石监码/银行专户/12345）在各处口径一致（规格书 §7 / `23` / `24`）**

### 1.3 可验证性 —— 每个需求能否被测试验收
- [ ] 每个 P0 模块有可测的验收标准（如：注册→实名→建档→发薪全流程可走通）
- [ ] **账户资金流可测**：工资代付、货款分账、退款、服务费分润各分支
- [ ] T 模块状态机（商品/订单/投诉/溯源/餐厨交接）可测试各分支
- [ ] 信用分构成（A3/I2/T2）有明确权重与计算口径（可出验收用例）
- [ ] 里程碑退出标准可量化（商户数、订单数、支付通道开通）

### 1.4 合规与风险 —— 法律/监管/资金红线
- [ ] **平台不沉淀资金、不做二清**：工资/货款全走第三方持牌通道（分账/代付产品）
- [ ] 强监管品类（农资/医美）明确只做信息撮合+溯源核验，不替代行政许可
- [ ] 实名认证路径明确（微信/支付宝实名回传优先，人工核验降级）
- [ ] 运营主体合规边界（政府牵头 + 国企/混合所有制运营）有预案
- [ ] 证据存证（时间戳+哈希）可支撑劳动仲裁/执法调取
- [ ] 支付通道申请主体与资质（营业执照/对公账户）有明确计划

### 1.5 范围与边界 —— 明确做什么、不做什么
- [ ] 明确不做：网约车/出租车（只做货运物流）、自建仓储物流（轻资产）、**自建资金池（二清红线）**
- [ ] 明确不做：政务对接（石监码/12345/银行专户均不可接，全部自建替代）
- [ ] MVP 范围外模块有明确分期安排，不模糊
- [ ] 试点城市=石家庄、试点行业范围明确
- [ ] **端形态明确：PC Web 优先，先 Web 后套壳桌面**

## 2. 评审会议议程（建议 1.5~2 小时）

1. **开场（10min）**：项目定位与目标回顾（一句话定位、三位一体、试点范围、**账户系统与 PC 端决策**）
2. **需求全景走读（30min）**：规格书 §4 功能范围 + §5 行业映射 + §6 优先级
3. **账户系统专项（20min）**：I1~I5 走读 + 支付通道可行性（`24-平台账户系统需求.md`）
4. **T 模块专项（20min）**：T1~T5 细化走读（`20-T模块用户故事细化.md`）
5. **里程碑与范围（15min）**：MVP 范围明细、不做清单、时间预期（`21-里程碑规划.md`）
6. **逐项评审（25min）**：按 §1 清单逐项核对，记录问题
7. **结论与待办（10min）**：确认通过 / 有条件通过 / 打回；记录整改项
