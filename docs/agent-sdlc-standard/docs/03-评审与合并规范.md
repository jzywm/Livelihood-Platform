# 03 · 评审与合并规范

> 目的:保证每个合入 main 的变更都经过充分的人工判断;明确谁可以合并、什么情况必须双审。
> 配套:`templates/.github/CODEOWNERS`、`checklists/PR评审Checklist.md`。

## 1. PR 生命周期

```
创建 PR → CI(G2)自动跑 → 门禁红则打回 → 人工评审 → 评审通过 → merge queue → 合并 main → 主分支验证(G3 merge-gate)
     ↑____________ 作者按评论修改(评审失效需重新通过)______________↓
```

- PR 描述必须包含:**改动内容、验证方式(测试/手工)、风险说明(是否涉及安全敏感目录)、依赖变更**。
- Agent 创建的 PR 必须带 `[AI]` 前缀(标题),并注明 Agent 版本/会话信息(见 `docs/06`)。

## 2. 评审角色与要求

| 角色 | 职责 |
|---|---|
| 作者 | 自测、写描述、响应评论、解决冲突 |
| Reviewer | 按 checklist 逐项审查,不走过场;可 Approve / Request changes |
| Code Owner | 敏感目录(CODEOWNERS 指定)的强制评审人 |
| 安全负责人 | 高风险变更的强制评审人(见第 3 节) |

评审要求:

- **至少 1 名 reviewer 批准**(非作者本人)。
- reviewer 与作者**不可为同一人**;Agent 提交必须由**人类**批准(Agent 互评不满足要求)。
- 高风险目录(`auth/`、`payment/`、密钥/CI 配置)按 CODEOWNERS 强制 owner 评审。
- 新提交推送后,旧评审自动失效(dismiss stale reviews),需重新通过。
- 评审响应 SLA ≤ 24h(工作时间);加急标记(热修)≤ 4h。

## 3. 高风险变更判定(触发双审 + 威胁建模)

满足任一条件即视为高风险变更:

- 涉及认证、授权、会话、密码/密钥管理
- 涉及支付、账务、资金或计费
- 涉及个人数据(PII)的采集、存储、传输、导出
- 新增或大幅修改外部依赖、网络通信、反序列化、文件处理
- 修改 CI/CD、部署脚本、密钥配置、生产环境配置
- 修改数据库结构或执行数据迁移

高风险变更处理流程:

1. 在 PR 描述勾选"高风险变更"并说明影响面。
2. 作者完成威胁建模(`docs/04` 模板),结论附在 PR 中。
3. 评审要求升级为:**2 名 reviewer(含 1 名 Code Owner)+ 安全负责人批准**。
4. 安全负责人可一键否决(Request changes),理由必须记录。

## 4. CODEOWNERS 机制

- 敏感目录由 CODEOWNERS 指定专属 owner(模板见 `templates/.github/CODEOWNERS`)。
- 分支保护开启 `Require review from Code Owners` 后,改动敏感目录的 PR 即使有普通批准,**仍须 owner 批准才能合并**。
- 建议最少配置:`auth/`、`payment/`、`secrets/`、`.github/`、`Dockerfile`、依赖清单文件。

## 5. Merge Queue(合并队列)

- 合并方式统一 **Squash**;开启 merge queue 后 PR 串行合并,避免并发合并互相踩踏。
- 队列中的 PR 会以最新 main 为基线**重新跑 required checks**(strict mode),防止"通过后过期"。
- 队列阻塞时按序执行,失败 PR 移出队列并通知作者。

## 6. 拒绝合并的硬条件(任一命中即打回)

- [ ] G2 门禁(SAST/SCA/构建/测试/覆盖率)任一失败
- [ ] 密钥扫描命中(无白名单豁免)
- [ ] 无人工批准,或高风险变更缺少双审/安全负责人批准
- [ ] 提交未签名
- [ ] 评论未 resolved,或 conversation 未关闭
- [ ] 高风险变更未附威胁建模结论
- [ ] PR 描述缺少验证方式或依赖变更说明

## 7. 评审质量要求(对 reviewer)

1. 按 `checklists/PR评审Checklist.md` 逐项核对,不要只看 diff 是否"看起来对"。
2. 关注**为什么**而不是**怎么改**:变更动机是否合理,是否有更简单方案。
3. 指出测试缺口:新逻辑是否缺少单测/集成测试,边界条件是否覆盖。
4. 发现安全问题时直接 Request changes,并引用 `docs/02-安全基线.md` 对应条目。
5. 评论具体、可执行;禁止"LGTM"式无内容批准。

## 8. 合并后验证(G3 merge-gate)

- 合并到 main 后,`merge-gate.yml` 自动执行:全量构建、全量测试、覆盖率门槛、密钥终检。
- 主分支任何时刻失败 = 最高优先级事件,24h 内修复或回滚(见 `docs/05` 回滚策略)。
