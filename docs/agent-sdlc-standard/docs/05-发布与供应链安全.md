# 05 · 发布与供应链安全

> 目的:让每个发布物(镜像/包)可验证、可追溯、可回滚;对齐 SLSA L2~L3。
> 配套:`templates/.github/workflows/release.yml`、`templates/trivy.yaml`、`templates/renovate.json`。

## 1. 版本策略(SemVer)

- 版本号遵循 [SemVer](https://semver.org/):`MAJOR.MINOR.PATCH`。
- 由 `feat` / `fix` 等 conventional commits 自动推导;发布 tag 与 `package.json` 版本**必须一致**(release.yml 校验,不一致即失败)。
- 预发布:`v1.2.0-rc.1` 供 staging 验证;正式发布 `v1.2.0`。

## 2. 发布流程(打 tag 触发 G4)

```
打 tag v* → release.yml → 版本一致性校验 → 构建镜像(含 SBOM+provenance)
→ Trivy 镜像扫描(高危阻断)→ 生成 SBOM(CycloneDX)→ cosign 签名(镜像+SBOM)
→ 发布 GitHub Release(附 SBOM 与签名)→ 金丝雀 → 全量
```

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 1 | 版本一致性校验 | 失败即中断 |
| 2 | 可复现构建(CI 固定工具链版本) | 失败即中断 |
| 3 | Trivy 扫描(CRITICAL/HIGH 阻断,忽略 unfixed 需在 `.trivyignore` 记录理由) | 高危 → 禁止发布 |
| 4 | 生成 SBOM(CycloneDX JSON) | 缺失 → 禁止发布 |
| 5 | cosign 签名镜像与 SBOM(keyless OIDC 或 KMS) | 失败即中断 |
| 6 | 发布产物归档(Release + 镜像仓库) | 人工介入 |
| 7 | 金丝雀发布 + 健康检查 | 异常 → 自动回滚 |

## 3. SBOM(软件物料清单)

- 每个发布物**必须**附带 SBOM(CycloneDX 格式),由 CI 自动生成(`anchore/sbom-action`)。
- SBOM 与签名文件随 Release 归档,保留策略与镜像一致(建议 ≥ 1 年,合规要求更长)。
- 用途:漏洞溯源、许可证合规、供应链审计。

## 4. 签名与 SLSA

- 镜像与 SBOM 使用 **cosign 签名**;推荐 keyless 模式(依赖 GitHub OIDC,无需长期密钥)或 KMS 托管密钥。
- 构建过程开启 `provenance`(SLSA provenance 记录),目标 **SLSA L2~L3**:

| SLSA 要求 | 本方案落地 |
|---|---|
| 源码版本控制 | Git + 提交签名(见 docs/01) |
| 构建脚本化 | CI 唯一构建入口,禁止本地构建产物直接上线 |
| 构建隔离 | GitHub Actions 托管 runner,一次性环境 |
| 可复现构建 | 锁定依赖 + 固定工具链版本 |
| provenance | `docker/build-push-action` 开启 `provenance: true` |
| 签名 | cosign 对镜像与 SBOM 签名 |

## 5. 镜像扫描策略

- 扫描时机:每次 PR 构建镜像(可选) + **每次发布强制**。
- 严重度阈值:`CRITICAL`、`HIGH` 阻断发布;`unfixed` 漏洞需逐条记录理由到 `.trivyignore`。
- 扫描结果(SARIF)上传到 GitHub Security 标签页,纳入漏洞 SLA 统计(`docs/02` 第 7 节)。

## 6. 依赖自动升级策略

| 工具 | 用途 | 策略 |
|---|---|---|
| Dependabot(原生)或 Renovate | 依赖升级 PR | 每周自动开 PR;patch/minor 门禁全绿可自动合并 |
| Dependabot security updates | 已知漏洞升级 | **不排队**,立即开 PR,门禁通过即合 |
| Renovate(如选用) | 分组、调度、自动合并控制 | 见 `templates/renovate.json` |

- 大版本(major)升级:人工评审 + 全量测试 + 必要时威胁建模复核。
- 依赖变更必须过 G2 门禁与评审(CODEOWNERS 覆盖依赖清单文件)。

## 7. 金丝雀与回滚

| 项 | 策略 |
|---|---|
| 金丝雀 | 新版本先接 5% 流量,健康检查(错误率、延迟、内存)观察 ≥ 15 分钟 |
| 自动回滚条件 | 错误率 > 2% / P99 延迟超基线 50% / 内存泄漏指标 / 关键告警 |
| 回滚方式 | 保留上一版本镜像(tag 不可变),一键切回;数据迁移类变更需单独设计回滚脚本 |
| 回滚验证 | 回滚后立即跑 smoke test,确认恢复 |

## 8. 发布审批与权限

- 发布动作仅**发布负责人**(或 CI bot + 人审)可执行;开发者本地**禁止**直接部署生产。
- 生产部署需记录:版本、变更内容、审批人、时间、回滚预案(见 `checklists/发布Checklist.md`)。
- 所有发布事件进入审计日志(谁、何时、哪个版本、哪个环境)。

## 9. 事故响应(发布后)

1. 确认影响面与严重度,按 `docs/02` 第 10 节漏洞响应流程处理。
2. 优先回滚到上一稳定版本,再修复 forward。
3. 复盘:根因、门禁为什么没拦住、改进项(新检查规则/新测试)。
