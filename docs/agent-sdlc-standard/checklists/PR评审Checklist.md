# PR 评审 Checklist

> 每个 PR 评审时逐项勾选。**任一关键项(⚠)不满足 → Request changes**。
> 高风险变更(见 `docs/03` 第 3 节)追加 `安全评审Checklist.md`。

## 1. 变更理解

- [ ] PR 描述包含:改动内容、验证方式、风险说明、依赖变更
- [ ] 改动与工单范围一致,没有夹带无关修改
- [ ] 一个 PR 只解决一个问题,提交粒度合理可回滚
- [ ] ⚠ Agent 提交:标题带 `[AI]` 标记;高风险变更附威胁建模结论

## 2. 正确性与设计

- [ ] 逻辑正确,边界条件(空值、超长、并发、重复调用)已处理
- [ ] 有更简单/更标准的实现方案吗(是否有过度设计)
- [ ] 错误处理:失败路径有兜底,不吞异常、不泄露内部细节
- [ ] 性能:无明显 O(n²)/N+1 查询/重复计算;涉及热点路径有评估
- [ ] 兼容性:接口变更是否影响调用方;是否有迁移/兼容层
- [ ] 并发安全:共享状态、锁、事务边界正确

## 3. 测试 ⚠

- [ ] 新代码单元测试覆盖率 ≥ 80%(行/函数/分支)
- [ ] 关键路径有集成测试;bug fix 有对应回归测试
- [ ] 测试是**有效断言**,不是空跑/只测 happy path
- [ ] Agent 提交:测试结果有真实输出证据,未删除已有测试

## 4. 安全(高风险变更必查,详见安全评审 Checklist)

- [ ] 输入校验 / 注入防护 / 越权(见 `docs/02` 第 3、4 节)
- [ ] 未新增硬编码密钥,密钥经环境注入
- [ ] 日志未记录敏感信息
- [ ] 依赖变更说明用途与替代评估;SCA 门禁通过
- [ ] 未放宽既有安全控制(如关闭校验、放宽 CSP)

## 5. 代码质量与规范

- [ ] 格式/Lint 通过(G0/G2 绿)
- [ ] 命名清晰,注释解释"为什么"而非复述代码
- [ ] 无死代码、调试残留、TODO 未处理(如有 TODO 需关联工单)
- [ ] 遵循项目架构分层,无循环依赖

## 6. 文档与发布

- [ ] 用户可见变更更新 README / API 文档 / 变更记录
- [ ] 涉及配置/部署,相关环境变量与文档已同步
- [ ] 是否影响发布(版本号、迁移、回滚预案)

## 7. 评审结论

- [ ] 所有评论已 resolved
- [ ] ⚠ 高风险变更:Code Owner + 安全负责人双审通过
- [ ] 结论:☐ Approve  ☐ Request changes(原因:__________)
