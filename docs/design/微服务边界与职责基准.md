## 2. 服务边界卡（逐服务）

### 2.1 账户服务 ACC

- **定位**：实名身份底座 + 纯记账簿，为全平台提供可信身份与资金流水证据。
- **对应功能点**：I-01 实名账户与钱包记账、I-06 强实名增强【M2】。
- **依赖（上游→本服务）**：微信/支付宝实名回传（唯一通道，强依赖）、支付通道（收款绑定）。
- **被依赖（本服务→下游）**：CRED、EMP、TICKET、TRACE、SETTLE、ASSIST 等（全平台实名/流水来源）。
- **数据归属**：§4.5 ① 身份域（`account`、`wallet_flow`）。
- **边界红线（不做什么）**：不设资金余额、不沉淀真实资金（R-01）；不接受人工证件核验降级（R-02）；不做对外 OAuth2 IdP（M3 候选）；NFC 强实名仅作高风险场景增强、基础回传不变。

### 2.2 结算服务 SETTLE

- **定位**：平台所有资金结算的**唯一执行层**，只走第三方持牌通道、平台不碰钱（记账与支付分离）。
- **对应功能点**：I-03 工资保障代付、I-04 商品购买结算分账【M2】、I-05 零工劳务结算【M2】、F-04 货运运费托管结算【M2】、平台结算账户（M0 对接层）、P-02 证据出证（结算侧）。
- **依赖（上游）**：ACC（实名/记账）、支付通道（微信商家转账/分账、支付宝、聚合）、EMP（考勤/用工关系）、JOB（对账/超时扫描）。
- **被依赖（下游）**：TRADE（分账触发方）、EMP（发薪履约数据）、CRED（信用更新）。
- **数据归属**：§4.5 ⑨ 结算域（`payroll`、`split_record`、`settle_flow`）——经 §4-C07 决策（2026-09-08）由 ③ 用工域/⑧ 交易域迁入，本文档以执行方 SETTLE 为权威归属。
- **边界红线（不做什么）**：不沉淀资金、不做二清、不设资金池（R-01）；不直接持有商户资金，仅过账通道；全部通道不可用即暂停资金入口并公告。

### 2.3 信用档案服务 CRED

- **定位**：商户/人员/供应商**信用档案与信用分中枢**，含价格公示基础版与未成年人禁入承诺标注。
- **对应功能点**：A-01 商户入驻核验建档、A-02 一店一档公开页、A-03 档案维护异常标记、A-04 价格公示（基础版）、A-05 未成年人禁入承诺标注、A-06 一人一档履历核验、A-07 信用分体系与红黑榜、A-09 未成年人交易拦截（「禁未成年」标记部分，下单校验在 TRADE）。
- **依赖（上游）**：ACC（实名）、TICKET（投诉归集）、TRACE（放心供应商联动）、AICORE（证照 OCR 预审）、OSS（证照存储）。
- **被依赖（下游）**：TICKET（投诉计入信用）、TRACE/PROD/TRADE/EMP/DASH（信用分读取与联动）。
- **数据归属**：§4.5 ② 档案域（`merchant`、`merchant_archive`、`price_list`、`commitment`、`person`、`certificate`、`credit_score`、`redblack`）。**`credit_score` 为商户/人员/供应商信用的唯一权威存储**。
- **边界红线（不做什么）**：不代定价（R-07，价目表仅展示）；不泄露 L1/L2 敏感数据（R-03）；**不承担供应商信用分公式计算**（T-05 公式在 TRACE，见 §3/§4-C02）。

### 2.4 用工服务 EMP

- **定位**：用工关系、入职年龄核验与劳务信用双向互评，落实未成年人保护与劳资信用。
- **对应功能点**：C-01 防童工入职年龄核验、C-02 打卡记工时（§5.14 新增）、I-02 劳务信用双向互评、E-03 招工求职【M2】。
- **依赖（上游）**：ACC（实名复用）、SETTLE（发薪履约数据）、CRED（信用并入）。
- **被依赖（下游）**：SETTLE（代付考勤校验）、PROFILE（履历数据源）、CRED（劳务信用分并入 A3/A2）。
- **数据归属**：§4.5 ③ 用工域（`employment`、`attendance`、`labor_review`）。`payroll` 已迁入 ⑨ 结算域 SETTLE（§4-C07 已决策），代付数据经 SETTLE 接口获取。
- **边界红线（不做什么）**：不另建身份核验体系（复用 ACC 实名）；不接受人工年龄核验降级（<16 岁强制拦截）；招工求职（E3）为 M2 范围、M1 不交付。

### 2.5 工单服务 TICKET

- **定位**：投诉/热线/申诉的**统一工单内核**，限时处理、升级市监、结果公示。
- **对应功能点**：D-02 投诉直达（含「未成年人违规进入」举报）、G-01 群众热线诉求、G-03 部门限时办结、D-03 恶意差评申诉与职业索赔识别【M2】、T-16 假货/假材料投诉直达闭环【M2，复用 D-02 机制】。
- **依赖（上游）**：CRED（投诉计入信用）、MQ（超时升级/催办）、OSS（证据直传）。
- **被依赖（下游）**：DASH（违规入场举报聚合→A-08 预警）、CRED（投诉率/信用联动）。
- **数据归属**：§4.5 ④ 工单域（`ticket`、`ticket_flow`、`ticket_evidence`）。
- **边界红线（不做什么）**：12345 不可接 → 自建工单 + 线下流转（P-04 双轨）；工单结果脱敏公示（R-03）；职业索赔识别仅 AI 辅助、人工确认后处置（C8）。

### 2.6 溯源服务 TRACE

- **定位**：供应商入驻核验、供应商信用、批次溯源码与扫码验真，落实「从种子到餐桌，全程透明」。
- **对应功能点**：T-01 供应商入驻资质核验、T-05 供应商信用档案与信用分、T-06 红黑榜与「放心供应商」动态标识、T-07 供应商扣分申诉、T-08 溯源批次码生成、T-09 扫码验真、T-10 溯源防篡改存证与异常预警、B-01 全链溯源贯通【M3】、B-03 抽检结果公示【M2】、B-04 店铺直播（§5.14 新增）、T-17 餐厨垃圾去向登记【M3】、T-18 收运企业信用档案【M3】、T-19 扩展品类资质门槛【二期】。
- **依赖（上游）**：CRED（供应商信用档案）、OSS（证照/图片存储）、存证（哈希链）、AICORE（直播画面识别 K-05）。
- **被依赖（下游）**：PROD（批次/资质关联）、CRED（放心供应商联动）、DASH（断链预警）。
- **数据归属**：§4.5 ⑤ 溯源域（`supplier`、`batch`、`trace_event`、`inspection`）。
- **边界红线（不做什么）**：强监管品类只做信息撮合 + 溯源核验、**不替代行政许可**（R-09）；供应商信用分公式（T-05）在 TRACE 计算，但结果统一写 CRED（见 §3/§4-C02）；不做北斗硬件对接。

### 2.7 助手服务 ASSIST（Python）

- **定位**：三端复用的智能助手侧边栏，执行「脱敏 → 意图 → 动作」，平台硬护栏强制。
- **对应功能点**：J-01 使用指导、J-02 页面跳转、J-03 对话内商品推荐、J-04 多轮上下文、J-05 兜底人工反馈、J-06 内容安全与幻觉管控、J-13 澄清式导购、J-15 助手操作悬浮卡 + 一键代做（§5.14 新增）。
- **依赖（上游）**：ACC/CRED/TRACE（经内部接口取数）、PROFILE（个性化推荐输出）、LLM（DeepSeek 开放平台）。
- **被依赖（下游）**：前端（三端侧边栏挂载）；PROFILE 的推荐输出消费方。
- **数据归属**：不落业务库（脱敏日志 ≤30 天）；会话 30 分钟 TTL 清空、不留跨会话记忆。
- **边界红线（不做什么）**：不直连主站数据库（走内部接口）；不开放 LangChain 自由工具/函数调用（R-05/C8）；不编造事实、不对外链；非竞价推荐、不杀熟。

### 2.8 商品服务 PROD

- **定位**：商品上架审核、选品广场检索与商品透明详情，支撑「全产业选品透明」。
- **对应功能点**：T-02 商品上架审核与批次关联、T-03 跨行业选品广场、T-04 商品透明详情页与供应商主页、T-21 采购决策辅助【M2】。
- **依赖（上游）**：TRACE（批次/资质关联）、CRED（供应商信用）、AICORE（图像/OCR）。
- **被依赖（下游）**：TRADE（下单商品来源）。
- **数据归属**：M2 商品域（§4.5 未单列，随 M2 补充 `item` 等表）。
- **边界红线（不做什么）**：只做撮合、**不代下单/不代定价/无包赚承诺**（R-08）；强监管品类仅信息撮合（R-09）；无竞价广告/隐性扣费（P-01）。

### 2.9 交易服务 TRADE

- **定位**：担保交易、货款托管、验收退款、争议仲裁与交易互评，实现「透明交易」闭环。
- **对应功能点**：T-11 担保交易与货款托管、T-12 到货验收与拒收退款、T-13 交易互评与信用联动、T-14 履约异常处置与防刷单风控、T-15 争议仲裁与结果公示、D-04 退货/退款（§5.14 新增）、T-23 上门服务（§5.14 新增）、A-09 未成年人交易拦截（下单校验部分）、T-20 消费者选购扫码验真（B2C 延伸，待确认）、F-01 货源发布与司机自由接单【M2，C05 已决策归 TRADE，接口设计随 M2 交付补充】。
- **依赖（上游）**：PROD（商品）、SETTLE（分账执行）、支付分账通道、CRED（信用联动）。
- **被依赖（下游）**：SETTLE（分账触发源）、CRED（交易互评→信用分）、DASH（交易合规监控）。
- **数据归属**：§4.5 ⑧ 交易域（`order`、`escrow`）。`split_record` 已迁入 ⑨ 结算域 SETTLE（§4-C07 已决策），分账由 TRADE 触发、SETTLE 执行并记账。
- **边界红线（不做什么）**：货款托管于持牌机构、**不碰货款 = 不二清**（R-01）；不代下单（撮合）；防刷单防作弊（R-15）。

### 2.10 监管看板服务 DASH

- **定位**：三端数据看板、**预警双向推送**与**费率/抽成公开公示**，实现从「事后抽查」到「数据驱动」。
- **对应功能点**：A-08 监管预警与分级监管、P-01 平台费率/抽成公开公示、F-05 货运费率公开（同 P-01 口径）、P-07 民生消费券（§5.14 新增）。
- **依赖（上游）**：各服务（数据聚合）、MQ（通知）、CRED（证照有效期）、TICKET（举报数据）、PROFILE（商铺画像，分级监管）。
- **被依赖（下游）**：监管端/经营端/消费端（看板与推送）。
- **数据归属**：§4.5 ⑦ 预警/看板域（`alert`）。
- **边界红线（不做什么）**：预警只推送线索、**不自动执法**（C8，人工复核后处置）；费率口径透明、调整前提前告知（P-01）；公示数据脱敏（R-03）。

### 2.11 画像服务 PROFILE

### 2.15 网关服务 GATEWAY（Java）

- **定位**：平台**唯一统一入口（API 网关微服务）**，承载接入层全部横切职责；AI 网关底座（K-02，模型路由）仍属 AICORE，与本服务分层不同、不并入（§4-C14）。
- **对应功能点**：无业务功能点——承载 PDD §3.1「API 网关与统一入口」拍板能力：路由转发、统一鉴权（JWT 验签 + Redis 吊销）、网关级限流（IP/账号/接口）、灰度分流、超时/熔断/降级、traceId 注入/透传、统一 Envelope、HTTPS 终结。
- **依赖（上游）**：Nacos（服务发现/灰度配置热更新）、Redis（JWT 黑名单 + 限流计数）、KMS（签名密钥注入）、云 WAF/高防、Prometheus/Alertmanager。
- **被依赖（本服务→下游）**：全部领域服务与四端（消费/经营/监管/运营）——所有前端流量唯一入口，前端不直连 Python 服务。
- **数据归属**：**无业务数据库**（无状态）；Redis 仅存 JWT 黑名单（短 TTL）与限流计数；路由/限流/灰度配置在 Nacos。不设 `openapi.yaml`/`er.md`（运维接口 M1 后期随独立部署补充）。
- **边界红线（不做什么）**：不做业务越权校验（2002 在服务内）、不做资金幂等（Idempotency-Key）、不做 BFF 协议聚合；服务端间接口（x-external-interfaces）不暴露于网关（仅内网 + 内部 Token）；密钥不出网关（KMS 注入）。
- **演进节奏**：M1 初期 = 应用内嵌统一 Filter + Nginx 过渡；M1 后期 = GATEWAY 独立部署（双实例）；M2 = 多实例全量 + Nacos 热更新 + K8s 金丝雀；GATEWAY 故障 → Nginx 直连单体兜底路径。

## 5. 服务排序与命名规范（建议）

- **排序**：以 §1 总表（= PDD §5 顺序 5.1~5.13 + 5.15 DELIVERY + 5.16 GATEWAY）为唯一排序；引用服务时用「缩写（大写）」，目录名用小写。
- **命名**：接口路径前缀统一 `/api/v1/{服务小写}/…`，与 §6.4 现有约定一致（`acc/settle/cred/emp/ticket/trace/assist/prod/trade/dash/profile/aicore/civic/delivery`）；`gateway` 为接入层服务、**无前端业务接口**（不参与业务路由前缀，运维接口 M1 后期随独立部署补充）。
- **跨服务写约束**：唯一权威存储 + 事件/接口上报；禁止跨域 JOIN/直读他域表（`32-功能列表.md` §2.3.1）。
