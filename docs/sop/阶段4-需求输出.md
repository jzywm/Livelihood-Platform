# 阶段 4:需求输出(Agent 起草 · 人类拍板)

> 目标:把已验证的痛点转化为**可开发的需求清单**,带优先级和验收标准,直接作为 PRD/排期的输入。
> 预计耗时:半天~1 天 · 负责人:Agent 起草,人类逐条确认
> 本阶段产出物 = "PRD 前置版",后续原型、技术方案都从它开始。

---

## 4.1 从痛点 → 需求的转化方法

对每个通过 G3 的痛点,问 4 个问题:

1. **用户要达成什么结果?**(结果 ≠ 功能。例:痛点"记不住喝水" → 结果"规律喝水",不是"做个打卡页")
2. **达成这个结果,最小闭环是什么?**(先做哪个环节能让用户马上受益)
3. **哪些环节用软件解决?哪些解决不了?**(解决不了的如实写"不做",别硬塞)
4. **这个需求的成功标准是什么?**(可测量的行为/指标)

### 转化示例

| 痛点(已验证) | 用户结果 | 最小闭环功能 | 成功标准 |
| --- | --- | --- | --- |
| 自习室订座要现场排队、经常没位 | 出门前就知道有没有位 | 实时座位余量查询 + 预约 | 用户到店前 30 分钟完成预约占比 >50% |
| 学习效率低、没人监督 | 每天有可执行的学习计划 | 每日计划生成 + 打卡提醒 | 连续 7 天使用用户占比 >40% |

## 4.2 MoSCoW 优先级模板

| 级别 | 含义 | 判定标准 | 排期 |
| --- | --- | --- | --- |
| **M(Must)** | 必须有,没有就不能用 | 直接服务核心痛点,砍掉则价值主张不成立 | 第一迭代 |
| **S(Should)** | 应该有,很重要但可后置 | 提升核心体验,但非生死攸关 | 第二迭代 |
| **C(Could)** | 可以有,锦上添花 | 加分项,资源富余再做 | 排期外 |
| **W(Won't)** | 明确不做(本期) | 与核心价值无关/成本高收益低 | 写入"明确不做清单" |

> 📌 W 级不是垃圾箱,而是**本期边界** —— 明确"不做"和明确"做"同样重要,防止需求蔓延。

## 4.3 需求清单模板(产出物 · PRD 前置版)

```markdown
# 需求清单:【产品名】v0.1(PRD 前置版)

## 一、产品定位(一段话)
为【目标用户】解决【核心痛点】,通过【产品形态】实现【核心结果】。

## 二、核心用户故事

## 三、需求明细

- 性能:____(如:首页加载 <2s)
- 平台:□ iOS □ Android □ Web □ 小程序
- 合规:____(隐私/资质)
- 数据指标:北极星指标 = ____(如:周预约完成数)
```

### 验收标准写法(Given-When-Then)

```
Given [前置条件],When [用户操作],Then [可观察的结果]
例:Given 自习室座位余量>0,When 用户提交 19:00-21:00 预约,
    Then 系统锁定座位并生成预约码,用户收到确认通知。
```

## 4.4 需求评审检查表(人类逐条过)

- [ ] 每条 MUST 需求都能追溯到已验证痛点/用户原话(无来源 = 删除)
- [ ] 每条验收标准可测试(不写"体验流畅"这种不可测词)
- [ ] MUST 数量 ≤ 总需求 50%,且单迭代 MUST ≤ 10 条(小步快跑)
- [ ] 已列出"明确不做"清单
- [ ] 北极星指标已定义
- [ ] 与阶段 3 访谈结论无冲突

---

## 4.5 决策门 G4(最终门)

| 问题 | 通过标准 |
| --- | --- |
| 范围是否可开发? | MUST 需求在 1~2 个迭代内可交付 |
| 每条需求是否有来源? | 全部可追溯 |
| 验收标准是否可测? | 是 |
| 是否明确本期不做什么? | 是,有 WON'T 清单 |

- ✅ 通过 → 本 SOP 完成 🎉 需求清单移交原型/设计/开发排期
- ⚠️ MUST 过多 → 砍到 1~2 个迭代量,其余降级为 SHOULD
- ❓ 存在未决问题 → 标注开放项,原型阶段同步验证
